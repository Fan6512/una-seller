# 接口层设计与调用范式（学它怎么设计接口，不是抄它做什么功能）

> **本文目标**：把智赢客户端→云端的接口层完整解剖，提炼**可复用的接口设计范式**与**必须避开的反例**，最后给出 Una Seller 自己的接口蓝图。
>
> **不做什么**：不提供重放/伪造请求的方法，不复现其会话令牌，不导出任何凭据。只做结构观察与设计评判。
>
> **证据来源**：`ZYing.Work.dll` 反编译（`ZClient` 2435 行、`ZResult`、`Member` 893 行）、`ZYing.UI.dll`（`Para`）、`ZYing.Core.dll`（`RecordSet` 382 行、`Record` 3790 行）。全部为静态反编译 + 运行时字段表交叉验证。

## 0. 一处必须修正的旧结论

`08` 与 `09` 报告里我写过「载荷走 XOR 加密，命令名受保护」。**这是错的。**

实测证据：

```
work_zclient.cs 全文搜索 Encrypt / Decrypt：
  private static byte[] Encrypt(byte[] arr)   ← 仅声明
  private static byte[] Decrypt(byte[] arr)   ← 仅声明
调用点：0 处
```

`Encrypt`/`Decrypt` 是**死代码**。`Init()` 直接把明文 `post` 写入 `NetworkStream`，`DoParse()` 直接从收到的 `byte[]` 解析，中间没有任何解密步骤。`_key` 字段还在，但没人用。

**正确结论**：

- **整条协议明文传输**，无 TLS、无签名、无加密
- 命令名在帧里是**明文字符串**
- 响应载荷是**明文二进制 RecordSet**
- `Member.Token`（Guid 会话令牌）**每次请求明文带在帧里**

这也解释了为什么两次内存转储能捞出 `spider.detail` / `spider.stat` 却没被解密——**它本来就没加密**。

> 对智赢这是一处严重设计缺陷；对我们是**最好的一课**：安全投入不能只做一半。它把字符串常量加密了（175 处解密调用、228 处模块字段引用），却把真正值钱的传输层敞开。

## 1. 三层接口拓扑

```
┌──────────────┐   ① HTTP/JSON（有 WASM 签名）   ┌──────────────────┐
│ 浏览器插件    │ ─────────────────────────────► │  seller.zying.net │
│ zying-ext    │   spider.check / spider.insert  │  /api 业务网关    │
└──────────────┘                                 └────────┬─────────┘
                                                          │
┌──────────────┐   ② 裸 TCP 明文二进制帧                    │  ③ HTTPS
│ WinForms 客户端│ ◄──────────────────────────────►         │  官方平台 API
│  ZYing.exe   │   命令 + 列式结果集                       │
└──────┬───────┘                                          ▼
       │                                        ┌────────────────────┐
       │ ④ HTTPS 拉图片缩略图                    │ Amazon SP-API      │
       └──────────────► seller.zying.com        │ api.mercadolibre.. │
                        image/bridge?url=       └────────────────────┘
```

四层职责分得很清楚，这是它**做得对**的地方：

| 层 | 协议 | 谁持有平台凭据 | 可调试性 |
|---|---|---|---|
| ① 插件 → 云端 | HTTP/JSON | 无 | 高（DevTools 可见） |
| ② 客户端 → 云端 | 裸 TCP 二进制 | 无 | **零**（无标准工具可用） |
| ③ 云端 → 平台 | HTTPS/JSON | **服务端** | 高 |
| ④ 客户端 → 图片网关 | HTTPS | 无 | 高 |

关键判断：**客户端不直连平台 API，不接触平台 Token**。这是整个架构里最正确的一条，也是我们必须照抄的一条。（例外：`Member` 里有 `Access`/`Secret`/`BToken`/`AliKey`/`AliSecret` 五个静态字段，属历史遗留，见 §8 反例 3。）

## 2. 帧格式逐字节解剖

### 2.1 请求帧

`Init(byte[] post)` 与 `GetPost(byte[] data)` 串起来，得到完整布局：

```
偏移   长度      字段              说明
──────────────────────────────────────────────────────────────
0      1        MethodType        'M'(77)=Data / 'N'(78)=GZipHeadr / 'W'(87)=Bytes
1      4        postLength        int32 小端，post 的字节数
5      4        LastUpdate        int32 小端，增量水位（响应里回填）
9      16       UUID              Guid，本次请求唯一标识
25     16       Token             Guid，会话令牌（Member.Token）
41     var      Command           BinaryWriter.Write(string)：7 位长度前缀 + UTF-8
41+n   4        headerLength      仅 GZipHeadr 模式：头块字节数
45+n   var      headerBlock       NameValueCollection 序列化（key/value 对）
       var      payload           业务载荷（RecordSet 二进制 / 裸字节 / 空）
```

**MethodType 用 ASCII 大写字母当枚举值**（`'M'`/`'N'`/`'W'`）——这是老式二进制协议的常见手法：抓包时肉眼可辨，比 `0/1/2` 友好。值得学。

**`CheckMethodType()` 的语义**：如果带了 headers 就把 `Data` 升成 `GZipHeadr`，否则降回 `Data`。也就是说 **header 块的存在与否由方法字节表达**，不是靠长度判断。这是省一个 flag 字节的技巧。

### 2.2 响应帧

`DoParse(byte[] back)` 逐字段读出：

```
偏移   长度      字段              处理
──────────────────────────────────────────────────────────────
0      4        LastUpdate        → 写回实例字段，下次请求带上
4      16       UUID              必须 == 请求的 UUID，否则抛 NoLoginEx
20     16       Token             必须 == Member.Token，否则抛 NoLoginEx
36     8        result            int64，业务返回码
44     1        isErr             bool，错误位
45     4        messageLength     int32
49     var      message           UTF-8 字符串
       var      …                 随后是 int32 长度 + RecordSet 二进制
```

**鉴权就是回显比对**（`guid != UUID || guid2 != Member.Token` → 抛 `NoLoginEx`）。

设计评价：

- ✅ 简单、零额外开销、能检测"会话被换掉"
- ❌ **不防重放**：任何能读到帧的人拿到 `Token` 就能构造请求
- ❌ **不防篡改**：没有 MAC/签名
- ❌ **不验证来源**：没有 nonce 或时间窗

> 这就是为什么我不做抓包重放——不是不能，是这件事对 Una Seller 零价值，而对他人的账号有实际风险。

## 3. 一次调用的完整生命周期

```
调用方                      ZClient                        服务端
  │                           │                              │
  ├─ PostAsync(Para) ────────►│                              │
  │                           ├─ SetSerial()                  │ ① 取序列号
  │                           │   _serial = Interlocked(ref Ticks)
  │                           │   写入 _ui.Serial（若绑定控件）
  │                           ├─ GetPost(data)                │ ② 组帧
  │                           │   LastUpdate+UUID+Token+Command
  │                           │   [+headers][payload]
  │                           ├─ Init(post)                   │ ③ 发帧
  │                           │   _mhead = [MethodType][len32]
  │                           │   连接池取 client / 新建 TcpClient
  │                           │   Write(_mhead) → Write(post)
  │                           ├─ Reading(readed) ────────────►│
  │                           │   循环读到完整长度             │
  │                           │◄──────────────────────────────┤
  │                           ├─ DoParse(back)                │ ④ 解帧
  │                           │   校验 UUID/Token → NoLoginEx
  │                           │   读 result/isErr/message
  │                           │   RecordSet.From(payload)
  │                           ├─ ThrowNotMatch()              │ ⑤ 丢弃判定
  │                           │   控件序列号已变 → IgnoreException
  │                           ├─ DoFinish()                   │ ⑥ 收尾
  │                           │   IsErr → ShowErr(throw)
  │                           │   否则 OnFinish() → DoHeader()
  │◄─ ZResult ────────────────┤                              │
  │                           ├─ Enqueue(this) 回连接池        │
```

**五个设计点**，逐个评价：

### 3.1 序列号做「取消」（这是它最好的一个设计）

`SetSerial()` 把 `_serial` 写进绑定控件的 `Serial` 属性；`ThrowNotMatch()` 在响应回来时比对：

```csharp
if (_ui is EControl ec && ec.Serial != _serial)
    throw new IgnoreException("…");   // 用户已经切走页面，结果丢弃
```

这是**用递增序列号实现「最新的请求才算数」**，等价于现代前端的 `AbortController` + `requestId` 竞态防护。在 2015 年的 WinForms 里能想到这个，水平不低。

**Una Seller 对应**：Tauri 侧用 `AbortController`，服务端不做特殊处理；关键是**前端必须实现**，否则快速切页会出现"旧数据覆盖新数据"。

### 3.2 响应校验前置

`DoParse` 在解析业务字段**之前**先校验 UUID 和 Token。不通过直接抛 `NoLoginEx`，不浪费后续解析。这是对的顺序。

### 3.3 错误分五级

| 异常 | 触发条件 | 调用方处理 |
|---|---|---|
| `NoLoginEx` | 响应 Token/UUID 不匹配 | 强制重新登录 |
| `IgnoreException` | 控件序列号已变 / `Closing=true` | 静默丢弃 |
| `IgnoreException(空)` | 声称长度超出剩余字节 | 静默丢弃（协议不匹配） |
| `Exception`（业务） | `result.IsErr == true` | `ShowErr` 弹窗 |
| 网络异常 | `ConnectAsync` 失败 | 重试 1 次后 `DoError` |

**四类不同处置**，比"一律弹窗"成熟。缺点：`IgnoreException` 用异常做正常控制流，性能上不优雅（.NET 里异常开销大）。

### 3.4 连接复用与回收

```csharp
ConcurrentQueue<ZClient> _pools;     // 每 IPGroup 一个池
ZClient Next;                        // 池内单链表
bool _busy;                          // 占用标记
void CheckExpired(); void Expired(int timeout);   // 空闲超时
void CloseAll();
```

`IPGroup.GetPoolClient()` 取空闲连接，用完 `Enqueue` 归还。**手写连接池**，不用 `HttpClient` 那套。

优点：零 GC 压力、连接永远热着、跨请求复用 TCP。
缺点：**没有上限控制**（并发 500 就开 500 条 TCP）、无健康检查、服务端重启后池里的死连接会导致首请求失败一次（靠 `trycount < 1` 重试兜住）。

### 3.5 `LastUpdate` 水位

请求带 `LastUpdate`，响应回填 `LastUpdate`，下次请求再带。语义是**增量水位**：服务端可以只返回"自该版本以来变化的数据"。

`RUNTIME_VERIFIED` 内存里见过 `spider.stat`、`spider.total` 这类统计命令，配合水位就是"轻量轮询变化 → 需要时再拉全量"的模式。

**这是最值得学的一条**，见 §7。

## 4. 契约三件套

### 4.1 `ZYing.Para` —— 一个 50+ 字段的通用参数袋

```csharp
public class Para {
    // 分页
    public int page, pagesize, maxcount, top;
    // 主键族
    public long id, pid, local;  public int userid, sectid, loginid, localid, from, aid;
    // 状态维度
    public int role, stat, type, flag, grade, level, result, term, rule, what, kind;
    // 搜索/范围
    public decimal low, high;  public int min, max;
    public string start, end, order, area, word, key, levels, grades, extra, abbr, lang, cur;
    // 数组
    public int[] accs, logins, sites;  public long[] ids;  public string[] values, keys;
}
```

**序列化方式**（这段是关键）：

```csharp
static Para() {
    foreach (FieldInfo f in typeof(Para).GetFields())     // 反射取字段
        list.Add(Expression.Call(Tool.Write, sr, Expression.Field(p, f)));
    _cacheWrite = Expression.Lambda<Func<Stream, Para, int>>(...).Compile();
}
```

用**表达式树在静态构造时编译**一个"按字段顺序逐个写"的委托（避免每次反射）。性能上聪明，工程上危险：

- **字段声明顺序 = 线上字节顺序**。在中间插一个字段，所有老客户端立刻错位
- 无版本号、无字段标签、无可选字段标记
- 50 个字段每个命令只用 3–5 个，其余填默认值照样上传
- 同一个 `stat` 在"采集列表"和"订单列表"里含义不同，靠约定

**评价：这是本文最重要的反例。** 它就是"为什么要有 OpenAPI/Protobuf"的活教材。

### 4.2 `ZYing.ZResult` —— 统一的四字段响应

```csharp
public class ZResult {
    public string Command;   // 服务端回显的命令名
    public bool   IsErr;     // 错误位
    public string Message;   // 错误消息（成功时为空）
    public RecordSet RS;     // 结果集
}
```

四个字段，覆盖了"哪个命令 / 成没成 / 为什么没成 / 数据在哪"。**简洁度上是对的**，比一堆 `{code, msg, data, success, timestamp, traceId}` 务实。

缺点：没有 traceId（出问题无法串联日志）、没有服务端耗时、没有分页元信息（藏在 `RS` 里）。

### 4.3 `RecordSet` / `Record` —— 列式结果集

```csharp
public class RecordSet : IEnumerable {          // 最多 255 个命名 Record
    public int Count;
    public Record Root => Create("root");
    public Record this[string name];             // 按名取
    public Record this[int index];
    public static RecordSet From(byte[] input);  // 反序列化
    public void Load(Stream sr);                 // byte 个数 + N 个 Record
}
```

```csharp
public class Record {
    public string Name = "";
    public RecordColumns Columns;        // ← 列集合，不是行集合
    public RecordColumn this[string name];        // 按列名
    public RecordColumn this[string name, int i]; // 按列名 + 行号
    public int Count, MaxCount, Page, PageSize, PageLimit;
    public int Scale = 18;               // 小数精度
    public const int FixSize = 60;       // 单元格定长
    public static int MAXLIMIT = 200000;
    public string Scope => "起始 - 结束";  // 人读的分页描述
}
```

**列式存储**：`Record.Columns["sale_title"]` 是一个**整列的值数组**，不是一个值。取值要 `record["sale_title"][3]`。

为什么这样设计：WinForms `DataGrid` 就是按列绑定，列式拿过来直接塞，**零转换**。这是 2015 年桌面端的正确选择。

代价：

- 无法表达嵌套（一个商品带 4 个变体 → 只能是 4 个平行列，或另开一个 Record）
- 无类型（全是 `object` 或 string，靠 `Scale` 和 `FixSize` 猜）
- 按字符串 key 取列，**列名改名即全线崩溃，且编译期无感知**

`RecordSet` 里最多 **255 个 Record**（一个字节计数），这是硬限制。超过就抛「数据集数量不能超过 255」——一个为多语言/多平台预留的容器，最后被 1 字节卡死。

## 5. 端点管理：11 个业务域分组

```csharp
public static IPGroup Server, 刊登, 香港, 网站, 美客多, N11, 速卖通, 速卖通远程, 择远, 老吕, 聚石塔北京;
public static IPAddress Address;  public int Port;
public static IPGroup GetOrCreate(IPAddress address);
```

**每个业务域一组独立的后端地址**。含义很清楚：

- 采集/商品走 `Server`
- 刊登走 `刊登`（独立集群，因为刊登是长任务）
- 港澳台/海外账号走 `香港`
- 各平台（美客多/N11/速卖通）各自独立集群

**这是微服务化的雏形**，只是没有服务发现——地址是编译进 `localhost()` / `zeyuan()` 这些方法里的常量。

评价：

- ✅ 按业务域隔离故障域，刊登挂掉不影响采集
- ❌ 地址硬编码在客户端，扩容/迁移必须发版
- ❌ `localhost()` 是 `[Conditional("DEBUG")]` 的调试开关，把 11 个组全部指向 `127.0.0.1`——**这解释了 U5 里那个 `127.0.0.1:8888` 的用途**（本地调试后端，正式环境不启用）

## 6. 十二条可学 / 十条反例

### 6.1 可学（`DESIGN` 建议采纳）

| # | 做法 | 为什么值得学 | Una Seller 怎么落地 |
|---|---|---|---|
| 1 | **命令 + 结果集统一契约**：一个通道跑全部业务，`{command, params} → {isErr, message, records}` | 协议面只有一套，新增业务零协议改动 | REST 上体现为**统一响应信封** `{ok, data, error, meta}`，而不是让每个接口长不一样 |
| 2 | **列式结果集** | UI 直接绑表，零转换 | **不学**（见 6.2 #10），但学它的"列表接口只返回列头 + 行数组" |
| 3 | **`LastUpdate` 增量水位** | 轮询成本从 O(全量) 降到 O(变化量) | `GET /collections?updated_since=<ts>` + `ETag`/`If-None-Match` |
| 4 | **序列号做取消/丢弃** | 解决切页竞态，比锁简单 | 前端 `AbortController` + 请求 id，服务端无感 |
| 5 | **连接池 + 空闲回收** | 长连接省握手，回收防泄漏 | 用 `undici`/`reqwest` 池，不手写 |
| 6 | **按业务域分组端点** | 故障域隔离 | 后端按 `collect` / `listing` / `media` 拆服务，前端用不同 baseURL 配置 |
| 7 | **错误分四级**（需重登 / 可忽略 / 业务错 / 网络错） | 不同处置不同 UI | 错误码前缀 `AUTH_*` / `CONFLICT_*` / `VALIDATION_*` / `UPSTREAM_*` |
| 8 | **上传进度回调** | 大文件必需 | `Tauri` 的 `invoke` + 事件通道 |
| 9 | **便捷重载阶梯**：`(name,value)` → `(N 个)` → `(批量)` → `(bytes)` | 90% 调用只需一行 | 后端不用管；SDK 层可提供 `client.get(path, {q})` 简写 |
| 10 | **命令名 `域.动作` 点号命名**（`spider.detail`） | 天然分组、可前缀匹配做权限 | 路由 `/v1/spider/detail` 同构 |
| 11 | **分页元信息随数据返回**（`Page`/`PageSize`/`MaxCount`/`Scope`） | 前端不用拼 | `meta: {total, cursor, hasMore}` |
| 12 | **方法字节用 ASCII 字母** | 抓包肉眼可辨 | 我们不用二进制，但同理：错误码用可读前缀而非纯数字 |

### 6.2 反例（`DESIGN` 明确避开）

| # | 反例 | 后果 | 我们必须怎么做 |
|---|---|---|---|
| 1 | **`Para` 通用参数袋 + 反射序列化** | 字段顺序即协议；插字段即破坏兼容；无必填校验；语义靠约定 | 每接口独立 schema（zod），**只传需要的字段** |
| 2 | **静态可变 `Member` 全局会话** | 单进程单账号；并发不安全；测试无法并行 | 会话按请求传入（JWT/session），无全局可变状态 |
| 3 | **客户端硬编码 40+ 客户 ID**（`public const int 测试号 = 1969;` `智赢杭州 = 1117;` …） | 客户定制必须发版；泄露客户名单 | 租户配置全在数据库，客户端只认 `workspace_id` |
| 4 | **明文 TCP + Token 回显鉴权** | 中间人可读可改；Token 可被窃取复用；无重放防护 | HTTPS 强制 + `Authorization: Bearer` + 短时效 + 刷新令牌分离 |
| 5 | **`Encrypt`/`Decrypt` 死代码留着** | 误导（包括误导了我两轮）；协议演进无清理 | 死代码删掉；协议变更写 ADR |
| 6 | **字符串常量加密但传输明文** | 安全投入全打在没用的地方 | 威胁建模优先：先保传输，再谈混淆 |
| 7 | **命令名是裸字符串** | 无类型、无补全、改名即断、无契约文档 | OpenAPI 生成类型，前端 `zod`/TS 双端校验 |
| 8 | **无幂等键** | 重复提交靠业务猜 | `Idempotency-Key` 头 + 服务端唯一索引（已写进 `10` §5.4） |
| 9 | **列式无 schema** | 按字符串 key 取列，改名编译期无感知 | 行式 JSON + 显式类型 |
| 10 | **一个 TCP 连接跑全部业务域** | 单点、无独立扩缩容、无独立限流 | 每域独立服务 + 独立限流 |
| 11 | **地址硬编码在客户端** | 扩容/迁移必须发版 | 配置中心下发 + 客户端只存 baseURL |

## 7. `LastUpdate` 水位：它最值钱的一个设计，但我们不照抄实现

**它怎么做的**：

```
请求帧 offset 5: LastUpdate（int32）
响应帧 offset 0: LastUpdate（int32）→ 客户端写回字段 → 下次请求带上
```

客户端本地存一个整数版本号，每次请求带上"我上次看到的版本"，服务端据此决定返回全量还是增量。

**它的问题**：

- 版本号是**全局单调 int32**，不是按资源。多个资源的更新会互相顶掉水位
- 语义不明确：是"最后更新时间"还是"最后变更序号"？从 `int32` + 名字 `LastUpdate` 看像时间戳，但 int32 存不下 2026 年的秒级时间戳（会溢出到 2038）——**这是它自己埋的雷**
- 没有 ETag，无法走标准缓存链路

**Una Seller 的做法**：

```http
GET /api/v1/collections?updated_since=2026-11-15T08:00:00Z&limit=50
If-None-Match: "v-8812"

→ 304 Not Modified                        （无变化，零 body）
→ 200 { data: [...], meta: { cursor, hasMore, server_time } }
```

三点差异，都是有意的：

1. **时间戳用 ISO8601 字符串**，不用 int32（避开 2038 + 时区歧义）
2. **按资源维度**，`updated_since` 是查询参数不是全局状态
3. **同时支持 ETag**，让中间层（CDN/反代）也能缓存

## 8. 平台 API 那一层：它藏起来了，我们得自己调

`OBSERVED` 客户端里与平台交互的类型：`ZYing.Mercadolibre`、`GetCatalogItem`、`SearchCatalogItems`、`PublishMartketResult`、`UpdateMarketItem`、`MeliAuth`、`GetDescription`、`GetDetail`、`GetMarketSiteInfo`、`X-Api-Key`、`https://api.mercadolibre.com`、`https://seller.zying.net/amazon/authback`。

**关键观察**：`Seller.zying.net/amazon/authback` 和 `/Meli/Authback` 是**授权回调**——说明 OAuth 流程是：

```
客户端 → 打开浏览器 → Amazon/Meli 授权页 → 回调到 seller.zying.net → 服务端存 Token
                                                                    ↓
                                                        客户端再来查"授权好了没"
```

**平台 Token 从不经过客户端**。这是我们该照抄的模式。

### 8.1 两块平台 API 的真实契约（公开文档，可直接学）

**Amazon SP-API**（`OBSERVED` 公开文档）

```
鉴权：POST https://api.amazon.com/auth/o2/token
      grant_type=refresh_token&client_id=…&client_secret=…&refresh_token=…
      → { access_token: "Atza|…", expires_in: 3600 }
请求头：x-amz-access-token: <access_token>     ← 注意不是 Authorization
       user-agent: <App>/<Ver> (Language=…; Platform=…)

取商品：GET https://sellingpartnerapi-na.amazon.com/catalog/2022-04-01/items/{asin}
             ?marketplaceIds=ATVPDKIKX0DER
上架：  PUT   /listings/2021-08-01/items/{sellerId}/{sku}     全量替换
改价：  PATCH /listings/2021-08-01/items/{sellerId}/{sku}     局部更新
取类目要求：GET /definitions/2020-09-01/productTypes?…         ← 上架前必查
批量：  POST  /feeds/2021-06-30/feeds  (feedType=JSON_LISTINGS_FEED)
```

> **重要**：SigV4 签名自 2023-10 起**不再需要**，只留 LWA token。这一点很多老教程还在写 SigV4，会白折腾一天。

**Mercado Libre**（`OBSERVED` 公开文档）

```
鉴权：Authorization: Bearer <access_token>（OAuth2）
取商品：GET  https://api.mercadolibre.com/items/{id}
描述：  GET  /items/{id}/description      → { plain_text, last_updated }
写描述：POST /items/{id}/description      body: { plain_text: "…\n…" }
改描述：PUT  /items/{id}/description
跨境：  GET  /marketplace/items/{id}/description?site_id=MLM&logistic_type=remote
```

> **两个坑**：① 描述**只收纯文本**，HTML 会被拒（`item.description.type.invalid`），换行只认 `\n`；② 跨境商品（CBT）必须带 `site_id` + `logistic_type=remote`，走 `/marketplace/` 路径而不是 `/items/`。

### 8.2 对照表：智赢的命令 ↔ Una Seller 的端点 ↔ 平台 API

| 智赢（明文 dotted 命令） | Una Seller 自家端点 | 最终落到哪个平台 API |
|---|---|---|
| `spider.check` | `POST /v1/collections/check-duplicate` | —（自家去重） |
| `amazon_hub.spider` | `GET /v1/sources/amazon/item?asin=` | —（插件/服务端解析） |
| `spider.insert` | `POST /v1/collections` | — |
| `spider.detail` | `GET /v1/products/{id}` | — |
| `spider.stat` / `spider.total` | `GET /v1/collections/stats` | — |
| （刊登） | `POST /v1/listings` | SP-API `PUT /listings/2021-08-01/…` |
| （取描述） | `GET /v1/products/{id}/text` | Meli `GET /items/{id}/description` |
| （类目属性） | `GET /v1/categories/{id}/attributes` | SP-API `/definitions/2020-09-01/productTypes` |

**注意右列**：Una Seller 的自家端点**永远不直接暴露平台 API 的形状**。理由：平台 API 会改版（SP-API catalog 从 `2020-02-01` 升到 `2022-04-01` 就是一次），自家契约必须稳定。

## 9. Una Seller 接口蓝图

### 9.1 三层，与智赢同构但每层换实现

```
插件 ──HTTP/JSON──► 自家后端 ──HTTPS──► 平台 API
桌面端 ─HTTP/JSON──►   ↑
                  （唯一持有平台凭据的地方）
```

**必须遵守的四条**：

1. **桌面端与插件都只调自家后端**，永不直连平台
2. **平台凭据只在服务端**，加密存储（`pgcrypto` 或 KMS），客户端永远拿不到
3. **授权走 OAuth 回调到后端**（学 `/amazon/authback` 这个模式），客户端只轮询"授权完成没"
4. **不发明二进制协议**——用 HTTP/JSON，让 `curl` 能用

### 9.2 统一响应信封

```ts
type ApiResponse<T> =
  | { ok: true;  data: T; meta?: { total?: number; cursor?: string; hasMore?: boolean; server_time: string } }
  | { ok: false; error: { code: string; message: string; details?: unknown; request_id: string } };
```

对比 `ZResult`：多了 `request_id`（串联日志）和 `meta`（分页），少了 `Command`（HTTP 路径已经表达）。

### 9.3 错误码前缀（替掉它的五级异常）

| 前缀 | HTTP | 客户端处置 | 对应智赢 |
|---|---|---|---|
| `AUTH_` | 401/403 | 跳登录 / 提示重新授权平台 | `NoLoginEx` |
| `VALIDATION_` | 422 | 字段级红字 | 无（它靠弹窗） |
| `CONFLICT_` | 409 | 展示"已存在，是否覆盖" | `ThrowNotMatch` 近似 |
| `UPSTREAM_` | 502 | "平台接口异常，稍后重试" + 原始错误折叠 | `ShowErr` |
| `RATE_LIMIT_` | 429 | 退避重试 | 无 |
| `INTERNAL_` | 500 | 上报 `request_id` | `DoError` |

### 9.4 五个必须先建的端点

```
POST   /api/v1/collections            采集入库（幂等）
GET    /api/v1/collections            列表（cursor + updated_since）
GET    /api/v1/products/{id}          详情（六个分区一次返回）
PATCH  /api/v1/products/{id}          局部更新（草稿态编辑）
GET    /api/v1/categories/{id}/attributes   类目属性（服务端下发）
```

`PATCH` 而不是 `PUT`：学 SP-API 的 `patchListingsItem`——**只传改动的字段**，避免"前端少传一个字段就被清空"的经典事故。

## 10. 怎么自己验证（不需要 hook，不需要还原算法）

既然协议明文，**验证成本已降到最低**。三条路，按合法性排序：

1. **看客户端自己的日志**（如果有）—— 最低成本
2. **抓本机自己的流量**（`Wireshark` / `RawCap` 抓回环，或 `Process Monitor` 看 TCP）—— 观察的是**你自己的连接、你自己的账号**，不涉及他人
3. **读磁盘上的 `.dat`** —— 已做，gzip 无加密

**不做的三件事**：不重放请求、不伪造 Token、不把抓到的会话用于任何自动化。原因不是技术，是这三件事一旦做了一次，前面 10 份报告就不能再作为**可公开引用的竞品研究**存在。

> 需要说明：本文写"命令名可从明文帧读到"，是为了说明**它的安全设计不成立**，不是提供抓取流程。对 Una Seller 的价值在于"别这么设计"，不在于"抄它的命令表"。

## 11. 一页纸总结

**智赢接口层的真实水平**：一个 2015 年代**工程上务实、设计上欠债**的内部 RPC。

| 维度 | 评价 |
|---|---|
| 协议效率 | 高。二进制 + 列式 + 连接复用，一个请求几十字节开销 |
| 协议可维护性 | **极低**。参数袋反射序列化、字段顺序即协议、无版本、无文档 |
| 可调试性 | **零**。无标准工具可用，只能靠客户端自己 |
| 安全性 | **不成立**。明文 + Token 回显 + 无签名，同时把力气花在字符串混淆上 |
| 分层 | **好**。插件/客户端/云端/平台四层职责清楚，客户端不碰平台 Token |
| 多租户 | **差**。40+ 客户 ID 硬编码进二进制 |
| 扩展性 | 中。加业务容易（加命令即可），改结构极难（字段顺序锁死） |

**给 Una Seller 的一句话结论**：

> 学它的**分层**（客户端永不直连平台）和**增量水位**（`updated_since`），
> 学它的**序列号取消**（前端竞态防护），
> **不要学**它的参数袋、全局会话、二进制协议、硬编码端点。
>
> 用 HTTP/JSON + OpenAPI + zod + 幂等键，把它的债全部提前还掉。
