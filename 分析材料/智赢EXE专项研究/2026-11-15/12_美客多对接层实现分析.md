## 1. 一句话结论

智赢对接美客多**不是一个适配器，而是一套双通道体系**：

- **主力通道是云端**：14 类刊登/更新任务、状态同步、类目映射、佣金/净收益计算、客服消息，全部由服务端执行，客户端只发命令 + 看日志。
- **客户端只保留 3 个直连口子**：**图片上传**、**商品视频（Clips）上传**、**跟卖扫描**（Buy Box 比价）。

这个切分的判据很实在：**凡是需要传大文件的、或者需要高频即时响应的，放客户端；凡是需要重试、事务、共享缓存、跨账号调度的，放云端。**

对应到 Una Seller：如果首版是 Tauri 桌面端 + 独立后端，**这个切分比例可以直接照搬**——图片/视频由桌面端直传平台，其余全部走后端。

## 3. 授权：OAuth 2.0 全流程，但密钥在客户端

### 3.1 三个静态方法撑起授权

```csharp
public static string GetAuthUrl(string siteId, string state = null)
public static async Task<TokenInfo> GetToken(string code, string siteId)
public static async Task<TokenInfo> RefreshToken(string refreshToken, string accessToken)
public static string ParseAppId(string accessToken)
```

`TokenInfo` 的契约（7 字段，OAuth 响应 + 错误提示合一）：

```csharp
public class TokenInfo {
    public DateTime ExpiresAt;     // 由 expires_in 换算
    public string access_token;
    public string refresh_token;
    public long   user_id;
    public string message;
    public int    status;
    public string error;
}
```

### 3.2 从 token 反查应用：一个很实用的技巧

```csharp
public static string ParseAppId(string accessToken)
{
    int num = accessToken.IndexOf('-');
    string text = accessToken.Substring(num + 1);
    return text.Substring(0, text.IndexOf('-'));
}
```

Meli 的 access_token 形如 `APP_USR-{appId}-{timestamp}-{hash}`。**从 token 第 2 段就能反查是哪个应用签发的**——所以 `RefreshToken` 不需要传 appId，只传 refresh_token 就能自动选对 `client_id`/`client_secret`：

```csharp
string text = ParseAppId(accessToken);
MeliAppInfo byAppId = MeliAppInfo.GetByAppId(text);
if (byAppId == null)
    throw new Exception("找不到应用:" + text);

// POST {AuthUrls[siteId]}
//   grant_type=refresh_token
//   &client_id={byAppId.AppId}
//   &client_secret={byAppId.AppSecret}
//   &refresh_token={refreshToken}
```

### 3.3 为什么要多套应用：一条踩坑注释

`MeliAppInfo` 里硬编码了**多套**独立应用（`ZYing` / `PuHui` / `JuYing` / `Cohere` / 本土，各含 `AppName`/`AppId`/`AppSecret`/`RedirectUrl`/`IsCbt`/`IsSelf`），其中一套带这样的标记：

```csharp
[Obsolete("之前的本土号后台登录不进去了，切换到 本土ZYing")]
private static MeliAppInfo 本土 => new MeliAppInfo { ... };
```

**这是本轮最有价值的踩坑情报之一**（**OBSERVED**，注释原文）。它说明：

1. Meli 应用会**因为合规审查或异常调用被封**，封了之后所有绑定该应用的店铺全部掉线；
2. 智赢的应对方式是**准备多套应用轮换**，把客户分散到不同 app 上；
3. 换应用意味着**已授权店铺必须重新授权**（token 与 app 绑定）。

> **给 Una Seller 的直接建议**
> - 单一 app 是**单点故障**。至少要准备 2 套（生产 + 备用），并把 `app_id` 存进授权表而不是硬编码。
> - **绝不把 `AppSecret` 放进桌面端**。智赢把 secret 硬编码在 `ZYing.Work.dll` 里，任何拿到安装包的人都能提取——这是**严重错误**，我们不做。
> - 授权表要留 `app_id` 字段，因为换 app 后旧 token 无法刷新，必须能识别"这个店铺绑的是哪个 app"，才能给出"请重新授权"而不是无限重试。

### 3.4 客户端只拿授权记录，不发起授权

`MeliApiBuilder` 从云端拉取授权记录并缓存：

### 3.5 Token 续期：15 分钟提前量 + 一个真实缺陷

```csharp
private async Task CheckToken()
{
    // 条件等价于：Now+15min >= _expire（即将或已过期）且 Aid != 0
    if (Aid != 0 && !_token.IsNullOrEmpty() && !(DateTime.Now.AddMinutes(15.0) < _expire))
    {
        if (_refresh.IsNullOrEmpty())
            throw new Exception($"账号{Aid}的刷新令牌为空");

        TokenInfo tokenInfo = await RefreshToken(_refresh, _token);
        _token   = tokenInfo.access_token;
        _expire  = tokenInfo.ExpiresAt;
        _refresh = tokenInfo.refresh_token;   // ← 只在内存里更新
    }
}
```

`SendCoreAsync` 每次请求前都会调它，所以**调用方永远不用关心 token 过期**：

```csharp
private async Task<HttpResponseMessage> SendCoreAsync(HttpRequestMessage request, bool throwError = true)
{
    await CheckToken();
    if (!_token.IsNullOrEmpty())
        request.Headers.Authorization = new BearerToken(_token);

    HttpResponseMessage rsp = await _h.SendAsync(request);
    string response = await rsp.GetString(100);
    if (!rsp.IsSuccessStatusCode & throwError)
        MeliErrorParser.Instance.TryThrow((int)rsp.StatusCode, response);
    return rsp;
}
```

**但这里有一个必须指出的缺陷（OBSERVED）**：`CheckToken` 刷新后只改内存字段，**没有回写云端**。

后果是：Meli 的 `refresh_token` 是**一次性**的（每次刷新返回新值，旧的立即失效）。如果同一个授权在两台机器/两个进程上同时使用：

```
机器A: refresh(R1) → 得到 R2，内存持有 R2，云端仍是 R1
机器B: refresh(R1) → 失败（R1 已被消费）→ 授权失效，用户必须重新授权
```

**这是"多端共享平台 token"的经典事故**。正确做法只有两条：
1. **token 只存服务端**，客户端所有平台调用都经服务端代理；
2. 若必须下发到客户端，则**刷新必须由服务端单点完成**，客户端只拉新 token，且在服务端加分布式锁 + 版本号。

> Una Seller 首版建议走第 1 条：**平台 token 永不出后端**。桌面端要传图时，让后端签发一个短时效的上传凭证，或干脆由后端中转（图片上传量不大，中转成本可接受）。

## 4. 传输层：极简 HttpClient，没有花活

```csharp
public const string ApiHost = "https://api.mercadolibre.com";
private static HttpClient _h;          // 静态单例

private string BuildUrl(string path)
{
    if (!path.StartsWith("http")) return path;      // 已是绝对 URL 就原样返回
    return ApiHost + path;
}
```

**注意 `BuildUrl` 的逻辑有点反直觉**：判断 `!StartsWith("http")` 时才拼 `ApiHost`——也就是**相对路径才拼**。这样设计是为了让少数方法能直传绝对 URL（比如图片下载）。

`SendAsync` 默认 GET，有 body 则用 `JsonContent`；`SendVersion2Async` 额外加一个 header（值被混淆，从命名推断是 API 版本协商，**UNKNOWN**）。

**没有做的事**（同样重要）：
- 没有 `RetryPolicy`（重试只在具体方法里手写）
- 没有 `IHttpClientFactory`（静态单例，DNS 变更不生效）
- 没有分页封装（每个方法自己拼 `offset`/`limit`）
- 没有限流器（Meli 是**按 app + 按 seller 双维度**限流，见 §9）

## 6. 数据契约：美客多的商品到底长什么样

### 6.1 `MeliItemInfo` —— `/items/{id}` 的完整镜像（49 个顶层字段）

这是最重要的一张表定义。全部字段（按 Meli 官方结构）：

```text
标识      id, site_id, catalog_product_id, catalog_listing, inventory_id
分类      category_id, domain_id, official_store_id
交易      price, original_price, base_price, currency_id, condition,
          listing_type_id, buying_mode, status, sub_status, tags
库存      initial_quantity, sold_quantity, available_quantity, variations
内容      title, subtitle?, pictures, attributes, descriptions,
          video_id, warranty, sale_terms, item_relations
物流      shipping, international_delivery_mode
卖家      seller_id, seller_address
时间      date_created, last_updated, start_time, stop_time, end_time
链接      permalink, thumbnail, secure_thumbnail, thumbnail_id
其他      health, net_proceeds, name, city, state, country, search_location
```

对应 Una Seller 的表设计启示：
- `status` + `sub_status` 是**两个字段**，不能合并（`active` + `out_of_stock` 是合法组合）
- `health` 是商品质量分（0–1），影响曝光，值得单独列
- `permalink` 必须存，客服/跟卖都要用
- `catalog_listing` 布尔值决定这个 item 是否挂在 catalog 下（跟卖场景的关键）

### 6.2 `MeliCateDto` —— 类目能力契约（16 字段）

**这是刊登功能的核心：类目决定一切约束。**

```csharp
public class MeliCateDto {
    public string Site;            // MLM
    public int    Id;              // 类目 ID
    public string Name;            // 西语名
    public string NameZh;          // ★ 中文名（云端翻译）
    public string FullName;        // 完整路径名
    public string FullZh;          // ★ 完整中文路径
    public bool   IsLeaf;          // 是否叶子（只能挂叶子）
    public int    ReferCbtId;      // ★ CBT 类目映射
    public string Domain;          // 类目域（如 MLM-CELLPHONES）
    public int    MaxTitleLength;  // ★ 标题最大长度
    public bool   AllowVariations; // ★ 是否允许变体
    public int    MaxVariations;   // ★ 最大变体数
    public int    MaxPictures;     // ★ 主图最大数
    public int    MaxPicturesVar;  // ★ 变体图最大数
    public List<MeliAttrDto> Attributes;
    public DateTime UpdateAt;
}
```

**这张表解释了刊登为什么要"先选类目"**：标题长度（60 / 200）、能不能做变体、最多几个变体（0 / 100 / 250）、最多几张图（10 / 12），**全由类目决定**。如果前端不按类目取这些值，校验必然错。

### 6.8 `ProductDescription` 是对象不是字符串

`CreateUserProductModel.description` 和 `SiteToSell.description` 都是 `ProductDescription` 类型（5 方法 2 字段）——**Meli 的描述是 `{plain_text, ...}` 结构化对象**，不是裸字符串。

这也印证了上一轮核对的公开事实：**Meli 描述只接受纯文本，HTML 会被拒**。所以描述字段必须：
1. 存 `plain_text`
2. 提交前**剥离所有 HTML**（采集来的描述常常带 `<br>`、`<p>`）
3. 长度上限按类目（有些类目限 5 万字符）

### 7.5 四维状态掩码：一个 int 表达四个维度

**这是本轮最有工程价值的技巧（OBSERVED）**：

```csharp
public enum NS { 产品 = 1, 图片, 价格, 库存 }   // 四个维度

public enum Stat { 待更新=1, 待删除=2, 失败=6, 完成=7, 零库存=8, 已删除=9 }

public static int Mask(int a, int c, int d, int e)
{
    return a * 1000 + c * 100 + d * 10 + e;   // 千/百/十/个位
}

public static int[] Union(NS ns, params Stat[] stats) { ... }  // 生成所有合法组合
```

含义：一个商品在**产品、图片、价格、库存**四个维度各自有独立状态，用十进制位编码成一个 int：

```
Mask(7,7,7,7) = 7777  → 产品完成、图片完成、价格完成、库存完成
Mask(1,7,7,8) = 1778  → 产品待更新、图片完成、价格完成、库存为零
Mask(6,9,7,7) = 6977  → 产品失败、图片已删除、价格完成、库存完成
```

配套的 `_stats` 是四组默认过滤值：

```csharp
_stats = {
    new[] { 1, 2, 6, 7, 9 },   // 产品维度全部
    new[] { 1, 2, 6, 7 },      // 图片（不含已删除）
    new[] { 1, 6, 7 },         // 价格
    new[] { 1, 6, 7, 8 }       // 库存（含零库存）
};
```

列表筛选时用 `Union()` 生成合法的掩码数组，一次 `WHERE mask IN (...)` 就能筛出"图片失败但产品正常"这类组合。

**代价**：掩码不可读、不可扩展（加维度就要改公式）、无法表达时间。**但在这个场景下（固定四维度、列表要快、组合筛选多）非常好用。**

> Una Seller 的取舍：首版不建议照抄。用四个独立 `smallint` 字段 + 组合索引更清晰，筛选用多条件 `WHERE`。**但如果列表数据量到百万级且筛选极频繁，这个技巧值得回头考虑。**

### 8.2 `UploadPic` 实现细节

```csharp
public async Task<MeliPicture> UploadPic(byte[] bytes, string fileName, int retry = 0)
{
    if (retry > 3) throw new Exception($"上传失败,重试{retry}次");

    var multipart = new MultipartFormDataContent();
    string ext = Path.GetExtension(new Uri(fileName).AbsolutePath);
    if (ext.IsNullOrEmpty()) ext = ".jpg";

    // ★ 用 GUID 重命名，不用原文件名
    string safeName = Guid.NewGuid().ToString("N") + ext;
    multipart.Add(new ByteArrayContent(bytes), "file", safeName);

    var request = new HttpRequestMessage(HttpMethod.Post, BuildUrl("/pictures")) {
        Content = multipart
    };
    return Deserialize<MeliPicture>(await (await SendCoreAsync(request)).Content.ReadAsStringAsync());
}
catch (HttpException ex)
{
    logger.Error(ex, $"上传失败 file={fileName} user={UserId} aid={Aid} retry={retry}");
    if (ex.StatusCode.In(429, 500, 502))          // ★ 只对这三个码重试
    {
        retry++;
        await Task.Delay(600 * retry);             // ★ 线性退避 600/1200/1800
        return await UploadPic(bytes, fileName, retry);
    }
    throw;
}
```

**四个值得抄的点**：

1. **GUID 重命名**：Meli 对文件名有编码要求，中文/空格/特殊字符容易出问题。用 GUID 彻底规避。
2. **只对 429/500/502 重试**：400（参数错）、401（token 错）重试没意义。
3. **`Path.GetExtension(new Uri(fileName).AbsolutePath)`**：能同时处理"本地路径"和"URL"两种输入。
4. **日志带 `Aid` + `UserId`**：出问题能定位到具体账号。

**两个不该抄的点**：

1. **线性退避**（600ms×n）。Meli 的 429 是**滑动窗口限流**，线性重试会继续撞墙。应当用**指数退避 + 抖动**（`2^n * base + random`），并把 `Retry-After` 头用上。
2. **递归重试**（`return await UploadPic(...)`）。栈会增长，虽然最多 3 层无实际风险，但语义上应该用循环。

### 8.3 幂等短路：已经在图床的图不再上传

`Meli图片上传.UploadImgCore`（**OBSERVED**）：

```csharp

{

    pic.Msg  = "上传中";

    // ★ 已经是 Meli 图床的图 → 直接复用
    if (pic.Url.IndexOf("mlstatic", StringComparison.OrdinalIgnoreCase) > -1)

        pic.Stat   = 10;                          // 成功

            pic.Msg = "上传失败:" + ex.Message;
            pic.Stat = 9;                          // 失败

            pic.Meliurl = meliPicture.SecureUrl;   // ★ 存 secure_url，不存 url
            pic.Height  = meliPicture.Height;
            pic.Width   = meliPicture.Width;
        }
    }
    catch (Exception ex)
    {

```

**这是整份报告里最值得直接照抄的一段**：

| 做法 | 为什么重要 |
|---|---|
| URL 含 `mlstatic` 就跳过上传 | 跟卖/复制别人的商品时，图片本来就在 Meli 图床，重传纯属浪费 |
| `GetImageId(url)` 反解 picid | 刊登只需要 picid，不需要重新上传 |
| 存 `secure_url` 不存 `url` | Meli 的 `url` 是 http，`secure_url` 是 https；前端直接渲染不会混合内容告警 |
| 记录 `width`/`height` | 用于前端占位、判断是否满足类目最小尺寸 |
| 三态 Stat（2 上传中 / 9 失败 / 10 成功） | 支持断点续传、失败重试、进度展示 |

## 9. 跟卖：不是抄商品，是监控 Buy Box

`Meli跟卖列表`（**OBSERVED**）：

```csharp
Record record = await LoadItems(await MeliApiBuilder.Create(p.aid), PTurn.Page);

private async Task<Record> LoadItems(MeliApi api, int page)
{
    MeliItemQuery query = ...;
    SearchSiteItemsResult result = await api.SearchItemsBySeller(query);   // ① 拉自己的 listing
    foreach (var item in result.results)
    {
        PriceToWinResult win = await api.PriceToWin(item.id);              // ② 逐个查能否赢购物车
    }
}
```

**"跟卖"的真实含义**：

1. `SearchItemsBySeller` —— 拉自己店铺的所有 listing（分页）
2. `PriceToWin(itemid)` —— 对每个 listing 问平台"**我要多少钱才能赢下这个商品的购物车**"

`PriceToWinResult`（3 方法 10 字段）包含 `status`（winning / sharing / losing）、`price`、`current_price` 等。

**这不是"抄别人商品"，而是"监控自己的商品有没有被别人抢走 Buy Box，以及要降价多少"。** 对多卖家共享 catalog 的场景，这是核心运营功能。

**为什么这一项放客户端直连**（而不像其他功能走云端）：

- 需要**实时**（价格变化以分钟计）
- 数量大（几千个 listing 逐个查）
- 结果不外发（只给自己看）

**它其实是最该走后端的一项**——因为 `PriceToWin` 是**每 item 一次请求**，5000 个 listing 就是 5000 次调用，必然撞上 Meli 限流。客户端直连意味着**每台机器各自撞墙**，而云端可以统一排队 + 缓存。

> Una Seller 若要跟卖功能：**必须放后端 + 队列 + 结果缓存**（如 15 分钟 TTL），绝不能让桌面端逐条打。

## 10. 状态同步：流式回推，不是轮询

`ZSyncMeli`（**OBSERVED**）：

```csharp
private static async Task 同步产品(int aid)
{
    if (_busy)
    {
        ZClient zc = ZClient.Create();
        zc.Command = <混淆>;
        NameValueCollection nv = new NameValueCollection {
            ["aid"]   = aid.ToString(),
            ["start"] = _start?.ToString(...),   // 增量水位：起始时间
            ["end"]   = _end?.ToString(...)      // 结束时间
        };
        if (Recieve != null) zc.Receiving = Recieve;   // ★ 流式接收
        await zc.PostAsync(nv);
        if (zc.IsErr) zc.Throw();
        Done?.Invoke((int)zc.Result, "完成");
    }

```

配合 UI 侧的回调：

```csharp

ZSyncMeli.Process = (string str, string no)               => { /* 更新当前行 */ };
ZSyncMeli.Percent = (int percent)                         => { /* 进度条 */ };
ZSyncMeli.Done    = (int num, string msg)                 => { /* 完成 */ };
```

**这是流式处理**：一次请求，服务端边同步边推送进度（`Receiving` 回调 + `Process`/`Percent`），不是"提交任务再去轮询"。

**注意一个实现缺陷（OBSERVED）**：`_busy` 是 `static bool`，`Start` 是 `async void`。`async void` 无法被 await，异常会直接抛到 `SynchronizationContext`。虽然包了 try/catch，但 `Start` 的循环里 `_busy` 标志在多窗口并发时**不是线程安全的**（没有 `Interlocked`）。

## 11. 站点与 ID 规则：`item_id` 前 3 位就是站点

```csharp
public static string GetItemLink(string itemid)
{
    if (itemid.IsNullOrEmpty() || itemid.Length < 3) return "";
    string siteid = itemid.Substring(0, 3);      // ★ 前 3 位 = 站点
    string value  = itemid.Substring(3);
    string baseUrl = SiteList.FirstOrDefault(i => i.Id == siteid)?.Url;
    if (baseUrl.IsNullOrEmpty()) return "";
    return $"{baseUrl}/{siteid}-{value}";        // → https://.../MLM-123456789
}
```

`SiteInfo` 的字段（8 个）：

```csharp

    public string Area;      // 地区码（用于选国旗图标）
    public string Currency;  // MXN
    public string Lan;       // 语言（es-MX / pt-BR）
    public int    Zone;      // 时区
```

## 12. 错误处理：分类 + 可重试判定

`MeliErrorParser`（**OBSERVED**）定义了错误处理骨架：

```csharp
public class MeliErrorParser : ErrorMessageParser
{
    private static Dictionary<string, string> 错误对照;   // 错误码 → 中文提示

    public override void TryThrow(int statusCode, string response)
    {
        ErrorMessage msg = Parse(response);
        if (!statusCode.Between(200, 299) || msg.HasError)
        {
            bool canRetry = CanRetry(msg);
            var ex = new HttpException(statusCode, msg.ErrorCode, msg.ErrorMsg, response);
            if (canRetry) ex.SetData("retry", true);     // ★ 标记可重试
            throw ex;
        }
    }

    private bool CanRetry(ErrorMessage msg)
    {
        // 9 条规则：错误码精确匹配 + 错误消息关键词匹配
        if (text.Contains("...")) return true;
        if (value.EqualIgnore("...")) return true;
        // ...
        if (text.Contains("...") && text.Contains("...")) return true;  // 组合条件
        return false;
    }

    public override ErrorMessage Parse(string response)
    {
        if (!Json.IsJson(response))
        {
            return new ErrorMessage { RawResponse = response, ErrorMsg = response };
        }
        MeliErrorCause cause = Json.Read<MeliErrorCause>(response);
        ErrorHandler?.Invoke(cause);     // ★ 全局错误回调（可用于埋点/告警）
        return new ErrorMessage {
            ErrorCode = cause.error,
            ErrorMsg  = cause.ToString(),
            HasError  = cause.HasError,
            RawResponse = response
        };
    }
}
```

`MeliErrorCause`（4 方法 4 字段）是 Meli 的标准错误结构：

```csharp
public class MeliErrorCause {
    public string error;         // 错误码，如 "invalid_access_token"
    public string message;       // 人读消息
    public int    status;        // HTTP 状态
    public List<...> cause;      // ★ 逐字段的详细原因
}
```

**`cause` 数组是 Meli 最有用的错误信息**——它会逐条告诉你"哪个字段错了、错在哪"：

```json
{
  "message": "Validation error",
  "error": "validation_error",
  "status": 400,
  "cause": [
    { "department": "items", "cause_id": 1001, "type": "error",
      "code": "item.attributes.invalid", "references": ["attributes"] },
    { "department": "items", "cause_id": 1160, "type": "warning",
      "code": "item.picture.quality.low", "references": ["pictures"] }
  ]
}
```

**必须解析 `cause[]`**，否则只能给用户"Validation error"这种无用提示，用户根本不知道该改什么。

> 智赢的实现有个弱点：`ErrorMessage` 只有 `ErrorCode`/`ErrorMsg`/`HasError` 三个字段，**`cause[]` 被 `ToString()` 拍平成一个字符串**。对刊登这种"一次提交几十个属性"的场景，用户需要的是"第 3 个属性 RING_SIZE 的值不在允许范围"，而不是一整段 JSON。

### 14.1 直接照抄（4 项）

| 项 | 具体做法 | 出处 |

|---|---|---|
| **多应用轮换** | 多套 app 硬编码 secret 在 DLL | 多套 app **存后端配置表**，secret 不出服务端 |

### 14.3 明确不抄（4 项）

| 项 | 原因 |
|---|---|
| **AppSecret 进客户端** | 拿到安装包即可提取，等于公开密钥 |
| **客户端逐条打 `PriceToWin`** | 5000 listing = 5000 次请求，必然限流；应后端排队 + 缓存 |
| **`sites_to_sell` 一次提交多站点** | 首版站点少（MLM 优先），一次一站更容易排错；等多站点真需要再上 |
| **7 个版本的 `MeliFreightLoader`** | 类爆炸；应做规则表 + 生效时间 + 灰度 |

### 14.4 五个先建的后端端点

```
POST /api/v1/platforms/meli/auth/url          → 返回授权 URL（带 state）
GET  /api/v1/platforms/meli/auth/callback     → 换 token，存库，不返回给前端
POST /api/v1/platforms/meli/categories/sync   → 拉类目树 + 中文名，入库
GET  /api/v1/platforms/meli/categories/{id}/attributes  → 类目属性定义（缓存 24h）
POST /api/v1/platforms/meli/images            → 接收桌面端上传的图片，转发 Meli，返回 picid
```

**注意第 5 个**：如果坚持"token 不出后端"，图片就不能由桌面端直传 Meli，必须后端中转。**这是首版最省心的选择**——图片上传量不大（一个商品 10 张），中转成本可接受，换来的是**没有 token 泄露风险、没有并发刷新的竞态**。

### 14.5 美客多对接的 8 条硬规则（都是从代码里读出来的）

1. **`item_id` 前 3 位是站点码**，不要当纯数字。（§11）
2. **描述只收纯文本**，HTML 必须剥离，长度按类目限制。（§6.8）
3. **属性值有三态**：`value_id`+`value_name` / 纯 `value_name` / `value_struct`（数字+单位），写错直接 400。（§6.4）
4. **必须在叶子类目上架**（`IsLeaf`），且标题长度、变体数、图片数都受类目约束。（§6.2）
5. **`refresh_token` 一次性**，并发刷新会让授权失效。（§3.5）
6. **批量读商品用 `/items?ids=`**（`GetItems`），不要循环单查。（§5.3）
7. **`PriceToWin` 是每 item 一次**，必须限流 + 缓存。（§9）
8. **CBT 是两段式**：global UP → local UP，状态 `CBT完成=3` 是中间态。（§7.3）
