# 09 · 内存转储与运行时证据（第四轮）

> 研究日期：2026-11-15
> 目标：智赢跨境 Windows 客户端（安装版）
> 方法：用户在自有机器上自行安装并运行客户端，用任务管理器生成全内存转储；本轮**只读该转储文件**，不 attach 进程、不注入、不 hook、不 patch、不改二进制。
> 结论标记：**RUNTIME_VERIFIED**（运行时直接观测）/ **OBSERVED**（静态可直接看到）/ **INFERRED**（推断）/ **UNKNOWN**

## 1. 对第 01–08 轮结论的修正

### 1.1 安装位置：不是 `C:\Program Files`

- **OBSERVED**：注册表 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\ZYing`
  - `DisplayName = 智赢跨境`，`DisplayVersion = 1.0.1.1`
  - `UninstallString = D:\跨境\ZYing\uninst.exe`
- **OBSERVED**：实际安装目录 `D:\跨境\ZYing`，**827 个文件 / 485 MB**
- 判定修正：`01` 报告里写的 `C:\Program Files\ZYing\1.0.1.1\` 只是 NSIS 脚本里的**默认值**，实际为用户自选路径。目录层级也**没有** `1.0.1.1\` 这一层。

### 1.2 CEF 确实随安装分发（推翻 `07` 的修正）

`07` §3 曾把 C13 改为"代码层有 CEF 采集器，但运行时不随包分发"。**这个修正方向是错的**。

- **OBSERVED**：安装目录中实测存在
  - `libcef.dll`、`chrome_100_percent.pak`、`chrome_200_percent.pak`、`icudtl.dat`
  - `locales\*.pak`（50+ 语种）
  - `swiftshader\`
  - `CefSharp.dll` / `CefSharp.Core.dll` / `CefSharp.Core.Runtime.dll`（1.86 MB）/ `CefSharp.WinForms.dll` / `CefSharp.BrowserSubprocess.exe` / `CefSharp.BrowserSubprocess.Core.dll`
- **INFERRED**：`ZInstall.exe` 只是**引导器**（13.5 MB），装完从网络拉取完整包（485 MB）。这解释了为什么我从 NSIS 载荷里只解出 70 个文件——那 70 个是引导器自带的 NSIS 插件、皮肤、5 个托管入口 DLL 和 apphost，**不是全部程序**。
- 因此 `07` 的"70 个载荷 = 全部内容"这个隐含前提不成立。

### 2.3 图片缓存命名规则（可直接借鉴）

**OBSERVED** 实例：

```
cache\cbu01.alicdn.com.img.ibank.o1cn01xnacnmgmbmb1wa3e!!22224245936080cib.jpg200x200.jpg
cache\http2.mlstatic.com.d601191cbt119089188810112026a.jpg
cache\http2.mlstatic.com.d603790cbt119838534545102026o.jpg
```

规则还原（**INFERRED**，二次转储后样本更充分，一致性很高）：

```
原 URL:  https://m.media-amazon.com/images/I/61kk9G-jBjL.jpg
落盘名:  m.mediaamazon.com.images.i.61kk9gjbjl.jpg

原 URL:  https://cbu01.alicdn.com/img/ibank/O1CN01…WA3e!!222242459360-80-cib.jpg_200x200.jpg
落盘名:  cbu01.alicdn.com.img.ibank.o1cn01…wa3e!!22224245936080cib.jpg200x200.jpg
```

变换步骤（四步，均可由上面两组样本验证）：

1. 去掉 `scheme://`
2. **整串转小写**
3. `/` → `.`
4. `-` 与 `_` **直接删除**（不是替换）；若 URL 尾带处理规格（`_200x200.jpg`），规格串保留并直接接在末尾

- 混合了 `alicdn`（AliExpress）、`mlstatic`（Mercado Libre）、`m.media-amazon.com`（Amazon）来源 → 跨平台共用同一缓存目录，靠域名前缀天然分区。

### 2.4 商品图片工作区（本轮最有价值的设计发现）

**OBSERVED** `image\818211505\` 内 10 个文件（4 主图 + 6 变体图）：

```
5c633a2f3077579343a0284db743cb5d.jpg      ← 32 位哈希名 = 主图
8338ab1c3e7349064261edeaaebbc4cf.jpg      ← 哈希名
d495788159be8f96efe76254c0089a3b.jpg      ← 哈希名
e6534c0a937c8e925505b0bdbb6f2720.jpg      ← 哈希名
DEEP.jpg      ESPRESSO.jpg   LIGHT.jpg

```

判定（**INFERRED**，强）：

- 目录名 = 商品 ID（9 位数字，与 `sale_id` 同型）
- **主图/通用图 → 内容哈希命名**（天然去重、天然幂等）
- **变体图 → 变体值命名**（`DEEP`/`ESPRESSO`/`LIGHT`/`MEDIUM`/`RICH`/`TAN` 是咖啡烘焙度，即变体选项值）

这是"变体图怎么落地"的一个非常干净的答案：不建索引表，用**文件名即语义**。对 Una Seller 有直接参考价值（见 §6）。

### 三个关键判读

1. **图片字段是三个独立槽位，不是一个列表**
   - `sale_picv` / `sale_imgsv`（后缀 `v` = variant）→ 变体图
   - `sale_swatch` → 色板/样本图（平台类目要求的 swatch）
   - `sale_main` → 主图
   - `sale_video` → 视频
   判定：**OBSERVED** 字段并存，**INFERRED** 语义。这与 §2.4 的目录实测（哈希名主图 + 变体值名变体图）互相印证。

2. **`sale_bullet` 与 `sale_intro` 始终并列**
   三轮证据闭环：插件 `sale_bullet`/`sale_intro` → `SpData._bullets`/`_intros` → `Sale` 的 `GetBullet/GetIntro` 与 `txtBullet/txtIntro` 文本框 → 运行时字段表。
   判定：**五点卖点与详细描述全程分离，是数据模型的一等公民**，不是渲染层拆分。

3. **`sale_en` / `sale_cn` 双语字段 + 平台属性模板键**
   内存中同时出现 `zh` / `es` / `pt` / `en` 与 `ATTR` `PSEUDO` `CHILD` `TAG` `CLASS` `PRODUCT_TITLE` `SKU` `PRICE` `GLOBAL_DATA` `HEADER_IMAGE_PC` `PRODUCT_PROP_PC` `DESC` `SHIPPING`。
   判定：**多语言字段与平台属性模板是两套东西**——前者是商品自身多语言文案，后者是刊登时向平台提交的属性树。

- **域名分工清晰**：`.com` 承担图片/静态资源网关，`.net` 承担业务 API 与平台授权回调。

### 5.4 五个独立子系统（这是本轮最重要的结构判断）

1. **词库子系统**（完全独立于商品）
   `产品标题词Detail`13、`产品标题模板`21、`产品标题导入`23、`产品侵权词`24、`产品风险词`19、`产品白名单`17、`产品替换词语`19、`Dialog.产品替换标题Dialog`9、`D变体词替换`7

2. **变体字典子系统**（平台间映射层）
   `Hepsi变体字典`16、`Ozon变体字典`16、`Temu变体字典`19、`Hepsi/Ozon变体参考`13、`Linio变体映射列表`17、`产品变体对照`21、`Detail.变体对照`7

### 9.5 失败项与根因（这一节比上面所有结论都重要）

| 尝试 | 结果 | 根因 |
|---|---|---|
| 找 JSON 响应体（`{"key":` 形态） | 仅 201 个窗口，**0 个**含 `sale_` 的 JSON 对象 | **协议不是 JSON REST**。与 `RecordSet`（`Columns`/`Count`/`Cursor`/`PageSize`）+ `ZClient.Encrypt/Decrypt` 的自定义帧完全一致 |

> **⚠️ 本表最后一行已被 `11` §0 修正**：`Encrypt`/`Decrypt` 在 `ZClient` 内**从未被调用**（全文 0 处调用点），是死代码。协议实为**明文二进制**，无 XOR、无 TLS。`11_接口层设计与调用范式.md` 给出了逐字节帧布局。
| 从「16:46 − 15:21」差集里找新解密字符串 | 新增 ASCII 44,287 条中，动词式标识符 **0 个**；新增"CJK" 60 万条全是伪汉字 | 两份转储堆布局不同，逐字节按 UTF-16 解码时**对齐错位**，产生海量假汉字。差集法在原始字节层不可靠 |
| 全量 dotted 标识符扫描 | 4,911 个候选，绝大多数是 JS 属性访问（`.length`/`.push`/`.map`）与 Chromium 的 C++ 源文件名（`statusbar.cpp`/`useragent.cpp`），真命令只有 `spider.*` 三个 | 内存里混着 CEF 渲染进程的 JS 与原生符号，SNR 很低 |

**根因总结（INFERRED，强）**：字符串解密**不做全局缓存**——明文只在调用瞬间的栈/临时对象里存活，调用返回后即被回收。因此**全内存转储天然拿不到完整命令名表**。

要拿只有两条路，且两条都不做：
1. **API hook / IL patch**：运行时截获解密函数入参 → 属动态改行为，越界
2. **还原解密算法**：属规避技术保护措施，越界

→ **结论：U2（RPC 命令名）到此为止，不再投入。** 已掌握 `ZResult.Command` 结构 + `spider.*` 命名风格 + 完整端点表，足够推出契约形状；命令名清单对 Una Seller 的设计没有决定性价值。
