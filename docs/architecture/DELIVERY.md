## M0：桌面基础与真实采集箱（当前）

### M0-00：先建立基础 CI

在 Issue #6 PR-A 之前，先以独立 Draft PR 提交最小 Go 与 Vite 检查，并取得实际 GitHub Actions 运行结果。**CI-0～CI-3 唯一技术配置/验收细节见 [CI_AND_RUNTIME.md](CI_AND_RUNTIME.md)**；后续按业务代码出现逐步添加数据库、Tauri 与 MV3 检查，本计划不重复维护第二套 CI 阶梯。

1. 复用已有 Tauri 2 + React + TypeScript 桌面工程和现有 Go HTTP 服务，明确 Go 为 M0-03 唯一业务后端，不再平行验证第二套 Fastify 服务（如出现具体阻塞再另议）。Windows x64 真机启动，macOS arm64/x64 构建与可用设备启动验证；不能只把 Vite 构建当成原生验收。
2. 以轻量模块注册组织 Core 和采集箱页面：统一主题、导航、状态与 API client；不建插件市场/多进程/多数据库。
3. 完成 PostgreSQL 持久化、商品采集结构化提交与去重、图片 URL/描述/五点/真实变体存储和查询。
4. 桌面采集箱列表/详情从**真实后端**读取，能搜索、看图片/卖点/规格/缺失原因；重启后可见。
5. 浏览器 MV3 插件先以 Amazon.com 美国站单商品人工点击入库并在客户端可见；随后适配 Mercado Libre MLM/MLB/MLA。
6. OAuth/云部署如条件尚不具备，单独标 BLOCKED，不阻断本地采集箱闭环；公网 API 必须鉴权和 HTTPS。

### 当前 Issue #6 的交付 PR 顺序

- PR-A：复用 Go API + PostgreSQL SQL 迁移 + 采集 POST/GET、幂等和真实读回；临时 PostgreSQL CI 验证断连重连、去重及部分采集不会抹除旧图、卖点和变体。**真实数据库进程重启持久性**由独立受控环境验证，不能以 CI 断连重连替代。
- PR-B：Tauri 2 采集箱真实列表、详情、图片/描述/变体/状态显示；配置 CSP 的图片来源/API 连接白名单及真实 CORS，CI 检查原生构建，真机启动状态另外验收。
- PR-C：Amazon.com 浏览器插件 → API → 桌面采集箱的单商品纵向闭环；增加 MV3 插件构建/清单检查，CI 不要求访问实时 Amazon 页面。

**M0 完成不意味着产品库、AI、图片白底或 Mercado Libre 刊登已实现。** 保持当前 Issue #6 的实施边界，不在 PR-A 提前建全套商品/店铺/发布数据表。

## M1：把采集资料转成可刊登商品（逐步可交付）

| 子阶段 | 模块/插件 | 最小交付 | 关键验收 |
|---|---|---|---|
| M1-A | **采集箱整理工作稿 + 产品库编辑器** | 第一切片：整理稿保存/重启恢复、独立产品箱持久化，先编辑标题/描述/内部备注；后续切片补齐图片、SKU、真实变体和价格编辑后再验收完整 M1-A | 原始来源不被覆盖；已整理来源可追溯，采集箱默认筛选未整理；转库后来源工作稿只读 |
| M1-B | **AI 文案插件** | 采集箱工作稿中生成英语基础稿、es-MX/pt-BR（需要时 es-AR）标题/卖点/详情候选；产品库也可调用，但只改 OwnProduct | 候选单独保存、可按字段采纳；来源快照及人工确认内容不被覆盖 |
| M1-C | **AI 图片插件** | 主图一键去背景/白底；保留原图、候选、选中结果和变体图关系 | 能前后对比并选择；不编造或修改重要商品外观；官方白底 API 未验证，不作依赖 |
| M1-D | **店铺只读同步与账号模板（OAuth 基础提前在 M0-ML-AUTH）** | 真实授权验收、同步账号原有已发布商品、识别账号支持站点并设置默认模板 | 旧商品无需关联 OwnProduct 也能出现在产品列表；只允许获准站点，Token 仅服务端保存 |
| M1-E | **多站点刊登 + 发布记录** | 选择账号和多个获准站点，按官方发布模型组织一次或多次 API 请求、逐站点记录成功/失败/待核实；与既有产品列表合并展示 | MLB 成功/MLM 失败等混合结果准确；HTTP 成功不等于全部目标成功，失败目标可安全重试，成功目标不重复发布 |

### M1 的发布边界

- **先保存与恢复整理工作稿，再做完整编辑器**。M1-A 的工作稿持久化可先行。M0-ML-AUTH 真店授权验收后，先做 M1-D 只读探查，再确定 M1-A 产品库编辑器字段，随后推进 M1-B/C 与 M1-E。
- **工作稿是转产品库前的暂存区，不是长期副本**。转库在单个事务内复制 title/description/notes 和真实来源快照；此后只在产品库继续编辑，来源工作稿一律只读，不再与产品双向同步。M1-A 第一切片用 `app.own_products.source_product_id UNIQUE` 与来源行锁判定是否已转库；保存已转库工作稿返回专用 409，来源 GET 返回 `own_product_id`，不要求本切片再新增 `converted_at`。以后若确需转库时间戳，可独立迁移补齐；重复通过只返回 `already_approved`，不能算新增成功。
- **未采全来源的转库策略**。第一切片允许 `partial` 来源经人工整理后转入产品箱（产品箱仍是待完善草稿，不代表可刊登）；不得把 `partial` 当成已具备全部上架属性。真正刊登前由类目规则、必填属性及人工确认再次校验。
- **多语言与站点归属（#59 增量）**。采集商品只保存一个来源与三份可独立编辑标题（英文/墨西哥西语/巴西葡语）；按明显语言特征识别并初始化，不能确定则暂放英文栏供人工调整；不在采集时自动分类，也不因商品拥有西语/葡语标题而绑定 MLM/MLB。工作台不选目标国家，不将类目当成一个站点属性；完成标题编辑后可以手动请求官方 CBT `/marketplace/domain_discovery/search` 分类候选，用户确认 CBT 通用类目或手动填写。该接口使用既有 CBT OAuth 店铺凭据，未连接时明确提示并保留手工入口。上传阶段才选择店铺/站点、当地售价、对应语言标题与站点必填属性，并按实际发布接口能力验证。
- **M1-A 编辑表单第二切片（PR #59）**。通过 `0009_listing_editor_fields.sql` 在来源工作稿和 OwnProduct 各增加受控的结构化 `listing_fields`，人工可编辑CBT 通用类目（ID/路径待用户确认及官方校验）、品牌/型号、主 SKU、GTIN、采购成本与币种、重量克数和包装长宽高（厘米）、卖点、附加属性、图片 HTTPS 链接与真实规格 SKU。转库时连同正文和来源快照复制，之后在 OwnProduct 单独改写，使用 revision CAS。**来源价格不是采购成本，也不是目标站点售价**；未填写尺寸不能编造默认值。
- **刊登前仍未满足的能力**。手动输入类目 ID 不是美客多官方类目预测/必填属性通过；图片 URL 调整不是永久托管/上传或 AI 修图；按站点的正式变体与平台有效 SKU 仍需官方账号能力、类目规则、站点映射及实际 API 联调后验收。PR #59 完成的是可保存、可恢复、可转库的资料编辑闭环，不代表可正式一键刊登。
- **产品库自持数据，来源只做溯源**。OwnProduct 的来源外键用 `ON DELETE SET NULL` 并另存来源快照（平台/URL/标题），不得级联于来源或工作稿——删采集商品、删源后重新采集都不能影响已转产品；重新采集只更新 `source_products`，需要参照时以只读方式对比，按字段手动拉取留到后续阶段。
- M1-D 先核对账号能力标签、已授权站点及物流子账号，读取一件有代表性的已刊登商品及站点记录，优先选多变体。对照官方类目属性和实际销售模型确认图片、变体、价格、包装及对象 ID。原始响应留在私有位置，仓库仅保存最小脱敏测试样本。
- 一次勾选多个站点是**用户操作**；后端按账号/官方模型决定是一请求包含多站点（如支持 `sites_to_sell`）或拆成多次，**按目标站点记录/回读结果**，不能机械规定每站点一请求。
- 平台 User Product、Global/Local UP、站点 Item 与变体关系必须依据**该账号的实时能力与当前官方文档**确定，不把智赢截图和逆向报告当官方协议。
- 类目/属性由官方能力驱动编辑表单；发布前人工确认；请求入队不等于真实发布成功。
- 站点示例：店铺 A=巴西+墨西哥，店铺 B=仅巴西；“西班牙语”是语言而非西班牙国家站点。
- 初期少量发布用单后端 + PostgreSQL 记录，必要时简单持久任务，不提前安装 Redis、Kafka、通用调度系统。

### OAuth、刊登和通知的阶段边界

- **M0-ML-AUTH 提前实现完整 OAuth 代码基线**（Issue #21 / Draft PR #23）：一次性 state、官方 Token 交换、CBT 主账号 + 各站点子用户映射、加密保存、Token 轮换（singleflight + PG 短租约）及 Go 服务端账号/站点门禁；其代码/Mock 验收不代表真实授权 PASS。**先完成此 PR 的代码审查/CI，再一次性配置服务器并真实联调**。M1-D 仍负责既有商品只读同步和模板，M1-E 负责实际刊登，不为 OAuth 安装 Redis。
- **M1-E 才做真实刊登**：先检查账号 `user_product_seller` 等能力，再适配当前 User Products 或尚支持的旧模型；不能直接套用旧 `/global/items` 创建链路；每目标站点分别追踪结果与错误。
- **M3 有真实运营需求时才做 Webhook/订单/客服**：通知入库后异步处理可以用 PostgreSQL + Go worker，实现前重新核实官方 topics、超时、鉴权和接口范围；M0 不建订单/消息表或通用队列。

## M2：真实商品管理与 AI 增强

根据已发布商品的高频操作，逐步增加改价、库存、图片/描述更新、状态同步、失败日志、必要的批量处理；AI 属性建议、翻译版本管理及其他助理能力按真实收益扩展。

- **产品库 → 已刊登商品的下行更新**：OwnProduct 的后续修改与来源回灌不同。M1-E 为每个店铺/站点 listing 建立映射和上次成功发布快照；M2 对比差异、逐目标提交与回读，分别记录成功或失败，失败目标独立重试，不盲目整包覆盖 Seller Center 的人工修改。
- **字段归属**：重量和尺寸是共用产品资料；站点售价与币种属于产品 × 站点。真正可写字段依据 M1-D 账号能力与官方读模型核实；修改物流规格可能影响运费，提交前必须提示。这里只冻结模型边界，**#52 不提前建 listing 映射表或开放更新接口**。

**完成标准**：一个真实账号的实际商品可以被准确识别、更新、回读，并能说明某次操作是否生效；错误不被隐藏。

## M3：按需运营

按工作频次选订单、物流、售前问答、售后、促销、利润分析及更高级图片处理；不预先完成所有智赢功能。

## M4：商业化（仍冻结）

支付、套餐、充值、订阅、计费、SaaS 管理后台、复杂多租户和团队 RBAC 均未授权实施。

### 现有服务器与本机工具链安排

运行环境选型遵循 [ADR-0005](../decisions/0005-m0-infrastructure.md) 和 [M0 部署基线](DEPLOYMENT_M0.md)：**已有 Ubuntu 服务器 + 现有 Nginx + Go API + Supabase 托管 PostgreSQL**，而不是默认自建 PG/Caddy。已有其他业务服务，部署前须在非公开会话检查兼容性；**基础设施选型不等于已上线或通过验收**。CI 在 GitHub Runner 完成，本机不必为了 PR-A 强制安装 PG/Docker；PR-B 实机显示真实商品前必须提供获批准的可达测试数据库 + Go API。任何公网部署须另行授权并具备 HTTPS、鉴权、备份；Windows/macOS 实机启动不可由 CI 编译代替。

## 开发与审查纪律

- 小 PR 各交付一个可运行结果；需求和代码放在约定目录；Draft → 审查 → Ready → Squash Merge，**负责人审核通过才合并**。
- 有直接来源的逆向观察只用于解释产品需求；不能引用或复制第三方代码、私有 API、内部鉴权。
- Win/Mac 不能因为 Windows 单机通过而同时声称 macOS 通过。
- 所有缺失字段与上传失败要诚实显示，不能用默认值假装采集到事实。
- 不为了 UI 截图复刻一整套长表单、审核中心、采集销量/评价、复杂 ERP 架构；必要安全：鉴权、HTTPS、官方 Token 服务端保存和真实写操作回读。

## V0.3 桌面测试版发布检查（PR #65）

此段是操作清单，不代表生产已部署或 Windows 真机已验收。正式签名发布与 PR 内的**未签名 QA 安装包**严格区分。

1. **合并前**：Go 更新路由的选择器、manifest 结构与资产检查、缓存回退、并发和 UI/字段定点测试通过；Desktop 类型检查和相关 CI 通过。使用临时签名 key 的 `signed_smoke` 只能证明隔离测试链路，不能作为正式签名 OTA 证明。
2. **合并**：负责人批准后才将 PR #65 合并 `main`；不提前打正式发布 Tag。发布工作流校验 Tag 所指提交必须在 `main` 历史内。
3. **服务端**：V0.3 客户端的唯一更新入口是 `https://mkd.186512.xyz/api/v1/desktop/updates`，Go API 在上游查询 GitHub Releases。Go 检查 manifest 结构、资产 URL 及签名字段是否存在。Tauri 下载时执行密码学签名验证。经独立授权部署 Go API/Nginx 后，确认更新路由及原业务路由可用。
4. **正式签名测试版**：核对 `desktop-production` 环境的审批和既有可信 Tauri 公私钥一致；在 `main` 中版本文件全部对应 `0.3.0` 后，由负责人创建 `desktop-test-v0.3.0`，通过受保护 workflow 生成签名安装器、`.sig`、`latest.json`；人工确认并发布为 **Pre-release**，不得发布 Draft 或用未签名 PR QA 包冒充更新包。
5. **首次手动安装**：下载与验收目标版本对应的 Windows x64 安装器，校验制品后手动安装。未签名 QA 包只用于功能验收。经批准的正式签名 V0.3 测试包建立后续 OTA 基线。历史客户端继续使用原有 GitHub `latest` 机制，首次升级按手动安装验收。
6. **端到端探测与后续真实 OTA**：先对唯一入口发起公开 GET 探测。正式通道发送 `X-Una-Include-Prerelease: 0`，测试通道发送 `X-Una-Include-Prerelease: 1`。有已批准的目标 Release 时，对应通道必须返回 200，且 JSON 的 `version` 与预期版本一致。仅在该通道无候选时接受 204。候选全无有效 manifest 且没有可用的同通道历史缓存时返回 503。探测通过后，从已手动安装且使用同一可信密钥签名的 V0.3 测试版出发，分别关闭和开启“接收测试版更新”。核对 `X-Una-Include-Prerelease: 0/1` 经 Tauri → Nginx → Go 传递。OFF 只检查正式 Release，ON 同时检查合格的 Pre-release。用更高版本验证下载、签名校验、安装和重启，同时核对同版本及更低版本不会触发升级。实机完成前记录 `MANUAL_PENDING(SIGNING, GUI)`。
7. **故障处理**：GitHub 单次请求上限 8 秒，Go 总检查时限 17 秒，包含等待并发请求、查询 Releases 和读取 manifest。Nginx 读取时限 20 秒，客户端检查更新时限 30 秒。上游失败或候选 manifest 全部无效时，返回同一通道上一次通过结构与资产检查的 manifest 并退避。
8. **后续 Beta 边界**：服务端已能识别 `desktop-test-v1.1.0-beta.N`，但 `windows-desktop.yml` 的 Tag 校验及生成 manifest 的版本比较**尚不支持**带 `-beta.N` 的 Tag；V1.0 以后要实际发布 Beta 时另改 workflow 和测试。本轮不提前开放。
