# Una Seller 精简开发路线（Delivery v2）

> 2026-10-26 · **自用优先，先能用；不做支付/订阅/商业 SaaS。** M0～M3 是实际里程碑，不规定固定工期；M4 暂停。
> 工作原则见 [FOUNDATION](FOUNDATION.md)。每阶段只开发足以满足验收的功能。

## M0：最小工程初始化

**目的**：从只有文档的仓库，得到能启动、能连后端、可继续开发的桌面程序。

仅做：
1. Tauri 2 + React + TypeScript 创建最小窗口，Windows 实际启动，macOS arm64/x64 至少构建并在可用设备上启动验证。
2. 一个简单的后端 HTTP 服务（Go 或 TypeScript/Fastify 通过最小验证后决定）；一个健康接口，前端可以读取。
3. 如接入店铺需要，建立最小 PostgreSQL 数据与迁移：店铺连接、授权信息等；暂不建设完整商品/订单库。
4. 具备开发者应用凭据与受控店铺时，跑通 OAuth → /users/me 只读调用 → Token 刷新/解绑。暂时拿不到授权时记录 `BLOCKED`，不得假装真实接口已经通过。
5. 最小检查：编译、基础单测、无提交密钥、一个 API 集成验证。CI 保持简单，避免频繁消耗 Actions。

**完成标准**：Windows 端程序可运行并访问后端；Mac 端构建与启动验证有记录；数据库可迁移；如具备授权条件则真实只读接口通过。没有授权时 M0 只能标记为部分完成。

**明确不做**：漂亮但空白的后台、全套设计系统、复杂登录设备管理、多租户、队列平台、AI Agent、订阅与支付、批量商品写接口。

## M1：商品真正能用

- 接入真实 Mercado Libre 商品数据，先实现跨境 CBT UP 与各站点（MX/BR/AR）的正确映射。
- 商品列表、搜索/筛选、详情、单条编辑、保存、回读、出错明确提示。
- 真实遇到批量操作需求再加入批处理；每个写操作要能确认对象、避免误改。
- **完成标准**：自己的测试店铺里可以安全、稳定地完成一项高频商品管理任务。

## M2：逐项增加 AI

- 优先 AI 标题建议（英语输入、墨西哥西语/巴西葡语分别校验长度与类目关键词）、描述/属性、翻译和客服草稿。
- AI 输出只是建议，人工确认后提交；模型供应商/网关可以替换。
- 不构建独立 Agent Gateway、向量数据库、模型计费和通用工具平台。
- **完成标准**：至少一个 AI 功能真正节省实际操作，并能发现明显的无效输出。

## M3：运营功能按需增加

订单/物流、客服/售后、库存、促销、利润与跨设备增强从高频痛点开始选择，不要求一次做完。后台任务积压、数据一致性问题出现后再引入持久队列或增量同步。

**完成标准**：每个新增功能都有真实场景、可验证的输入输出和最小错误恢复方案。

## M4：商业化（当前冻结）

支付、套餐、计费、充值、销售后台、多租户商业化、复杂组织 RBAC **均不在当前开发任务中**；未来决定面向第三方卖家销售时再独立立项。

## 开发节奏

- 以小 PR 交付一个可验证结果，先做一条纵向闭环而不是一次搭所有基础设施。
- 每个 PR 说明：解决的问题、最简实现、验证结果、新增依赖理由（如有）、哪些事情明确没有做。
- 非功能需求只保留够用的边界：平台令牌不泄露、公网接口不能无鉴权、商品写操作正确、Win/mac 构建不过度破坏。
- 不预先安装 Redis、River、Event Bus、KMS 平台、微服务或复杂日志系统；需要时用具体指标说明理由。
