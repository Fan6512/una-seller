# Una Seller 领域与执行最小契约（v2.1）

> 2026-11-15 · 目的：避免错误的商品身份模型和危险的重复写操作；**不是要求提前实现完整领域驱动/事件溯源系统**。

## 1. 从最小对象开始

### 平台接入侧概念（用于理解官方对象，不直接作为自研数据表清单）

- `StoreConnection`：店铺授权连接；自研侧沿用同名对象，账号刊登模板另由 `StoreTemplate` 管理。
- `MarketplaceSeller`：官方账户或各站点卖家身份，属于 StoreConnection 读取的官方信息。
- `UP Product / Product Family / Variation`：官方 UP、商品家族与变体概念；应通过 **PublishedListing** 的平台对象映射表示，不直接等同 **OwnProduct** 或来源变体。
- `Site Listing`：站点侧真实商品和销售条件，在自研侧对应 **PublishedListing** 的站点对象。
- `Draft / Operation`：通用解释“草稿/外部操作”，并非统一实体名；自研侧将**采集整理工作稿 CollectionWorkingDraft**、**自有商品草稿 OwnProduct**、**刊登操作 PublicationOperation** 严格区分。

以下六个业务侧对象才是 Una Seller 的分阶段数据边界。平台侧概念与业务对象通过官方 ID/授权关系映射，不要求一一对应，尤其不能把 `Draft` 混用为采集工作稿和产品库草稿。

M0 只建立真实接口需要的数据表，不提前为订单、退款、广告、团队、多租户和向量数据库创建空表。M1 再完善 UP 与本地 Item 的关联。

**不变量**：一个全球 UP 不能简单等同于一个站点 `item_id`；不能把不同站点的价格/币种合并；金额不能使用浮点数做最终计算。

### 从采集箱到产品列表的最小身份规则

按阶段建立真实需要的数据对象，而不是一次建完商业 ERP：

1. **SourceProduct / 采集箱**：用户 + 来源平台 + 站点 + 规范化来源 URL 唯一；包含原始标题、普通描述、按顺序的卖点、图片 URL、实际来源变体、采集状态和警告。不得因 AI 编辑或再次采集覆盖人工已经确认的自有商品。来源采集合同**不增加**销量、评价、卖家、独立 ASIN、品牌列。
2. **CollectionWorkingDraft / 整理工作稿**（M1-A 基础、M1-B 加入 AI）：绑定采集箱来源，但与 SourceProduct 原始快照**独立存储**；可保存人工补充和后续 AI 候选、重启后恢复。转入产品库后保留来源记录与追溯关系，采集箱默认筛选未整理记录，允许查看已整理并再次整理。不要求 M0 预建工作稿表。
3. **OwnProduct / 产品库**（M1-A 才创建）：自有可编辑草稿，可追溯来源，持有人工补充真实材质、重量、包装、成本、SKU 等。采集内容复制成初稿后独立演化；同一来源可以产生多个草稿。产品库内 AI 重新生成只更新 OwnProduct 草稿，不回写 SourceProduct 或原整理工作稿。
4. **StoreConnection / StoreTemplate**（M1-D 才创建）：真实账号 OAuth 与有权限站点；模板只是默认勾选和站点销售参数，不代表授权。
5. **PublicationTarget / PublicationOperation**（M1-E 才创建）：每个店铺×站点**业务目标**单独记录状态、错误与回读；官方 API 可以按账户当前发布模型用一个请求处理多个目标站点，不能假定一站点一请求。请求 ID/目标状态与官方对象 ID 分开。
6. **PublishedListing / 产品列表**（M1-D 先只读、M1-E 增加自建刊登）：包括授权账号**原有**经官方只读同步的真实商品和本系统新发布并确认的对象。原有商品允许暂时没有 OwnProduct 或本系统发布任务，后续按需关联；一个 OwnProduct 可对应多个店铺、站点、平台对象。Global UP / Local UP / Item / Variations 具体关系按账号和官方当前协议映射。

采集状态（complete / partial）、草稿准备度（draft / ready）、发布操作状态（pending / processing / success / failed / needs_check）以及平台商品状态**不得共用一列**。金额使用精确 decimal；来源缺失的价格/图片/重量应为 null 或明确的缺失状态，不能填 0。

### M0-03 采集入库契约：防止旧式单表覆盖设计回流

- M0-03 仅落实最小用户身份、`source_products`、`source_product_images`、`source_product_variants`；这属于采集来源数据，**不是**可刊登产品草稿。采购成本、真实重量尺寸、供应商和未来 AI 候选应由 M1-A 的独立整理工作稿承载，不作为浏览器采集必填项。
- 唯一去重依据为**所属用户 + 来源平台 + 来源站点 + 规范化来源 URL**，不引入必填 `source_product_id` / 独立 ASIN。一个平台商品在不同站点或不同账户下不能仅因平台商品 ID 相同而误合并。
- `description` 与按原始顺序保存的 `bullet_points` 分开，图片保留主/附图顺序，规格保留实际存在的属性组合及图片/价格关联；可在子表中对动态属性使用 JSONB，但不以此代替清晰的子项关联。
- **重复采集更新必须区分“本次未读取到”和“明确读到了空值”**：部分/失败采集不可用 `ON CONFLICT DO UPDATE` 无条件覆盖已有完整图片、变体或文案；按来源完整性与字段可信度选择保留/更新，事务中保证主商品和相关子项一致。金额使用 `numeric` 或等效精确类型，经 API 使用十进制字符串，未知值为 null 而非 0。
- HTTP 层区分“首次保存、重复更新、部分已保存”和“请求失败未保存”；失败未保存不是采集箱中一条已保存的商品记录。首个 PR-A 使用**纯合成测试数据**验证新增、更新、字段保留和实际 PostgreSQL 读回。
- 不直接采用从第三方方案得到的 `collected_products` 单表结构、以来源 ID 去重或清空历史图/变体的样例 SQL；以 [ERP-MVP](ERP-MVP.md) 与 [Issue #6](https://github.com/Fan6512/una-seller/issues/6) 为准。

**源图 / 自有素材版本**：来源图片与自有编辑图片引用分离；AI 白底候选不能覆盖原图，刊登选中图要能追溯；不因图片白底功能提前创建对象存储和多媒体服务。

## 2. 官方 API 接入

只用 Mercado Libre 官方 REST API；业务层不使用第三方私有协议、解密组件、Cookie 自动化。

先用一个简单的 `MeliClient` 包装认证、HTTP 请求、错误转换和基本限流。功能变多再按商品/订单模块拆分，不提前建复杂 Adapter + Gateway + Repository 三层。

官方端点、站点权限、参数和 API 行为必须参考官方文档并用有权限的账号验证。研究材料的 68 个直连端点不能直接当作自研 API 规格。

### 官方接入何时展开

- M1-D 才实现 Mercado Libre OAuth、Token 更新/刷新、店铺只读同步。并发刷新可使用 PostgreSQL 行锁或其他轻量事务方案协调，具体 Token 有效期及轮换语义以官方当期文档和账号实际响应为准，**不为未来 Token 刷新在 M0 预装 Redis**。
- M1-E 根据当前账号是否启用 `user_product_seller` 选择 User Products 或仍受支持的 Legacy 操作，不把任何一份旧 CBT API 清单当成所有账号通用合同。参考 [User Products 官方说明](https://global-selling.mercadolibre.com/devsite/manage-sales-global-selling/user-products-cbt)；各目标站点单独记录状态和平台 ID，API 请求数量由实际模型决定。
- M3 出现真实订单/问答/售后需求后再验证 Webhook topics、返回要求和接口权限，可先使用 PostgreSQL 持久通知/任务与 Go worker，不因历史逆向资料提前增加 `meli_orders`、`meli_interactions` 等空表或 Redis。

## 3. 真实写操作的最低保障

基本流程：**选择正确店铺与商品 → 校验修改 → 用户确认 → 官方 API 写入 → 回读结果 → 展示成功/失败/待核实**。

- 要保存操作 ID/目标/关键状态，使失败可查；不要求先建通用审批系统。
- 超时不代表写入失败：能回读时先回读，避免重复修改。
- 不把“重试”或“幂等键”当作官方平台恰好执行一次的保证。
- 少量单条操作可同步处理；批量或耗时任务真正出现时引入简单持久任务，再视需要选择库。
- 不可逆操作（例如已发消息、退款）必须明确提示，并保留人工确认。

### 多目标刊登最低执行规则

- 发布前确定用户选择的 OwnProduct、店铺账号和每个目标站点，逐站点执行类目/属性/图片/币种/物流校验。
- 模板仅选择默认站点、默认销售参数；若站点无授权或当前账号发布模型不支持，必须禁用而非提交尝试。
- 一个 UI “多站点发布”可能通过**一次官方请求包含多个站点**，也可能因账号/刊登模型拆成多次请求；请求形态由官方协议决定，业务上仍对每个目标独立记录结果，不能因为某个站点失败就重试已成功的站点。
- 解析官方返回中各目标站点的结果（支持时包含 `site_items[]`），并以官方返回或后续只读回查**确认目标已发布**后创建/更新 PublishedListing。HTTP 200、操作入队和总体请求成功均不代表所有站点成功。超时/网络中断标记 needs_check，先回读后重试。已授权账号已有商品通过只读同步独立进入 PublishedListing，无需伪造 OwnProduct。
- 失败提示要展示官方字段级 cause/error 信息（可用时），让用户定位到编辑字段；日志脱敏且不包含 Token。

## 4. AI 最小边界

AI 文案从采集箱由用户主动触发：原始采集事实 + 已保存的人工补充资料 → 标题/卖点/详情/语言候选；候选保存在**来源关联的整理工作稿**，人工选择采纳后进入 OwnProduct。产品库内继续生成候选时只修改 OwnProduct，不反写整理工作稿与来源快照。不得编造不存在的材质、认证、功能。客服 AI 属后续按需模块。

图片插件支持带使用权素材的背景去除/白底候选、对比及人工选用；官方图片诊断、上传和 AI 修图不是等价接口。官方白底 API 是否对第三方开放需要专项核实，不能预设存在。

模型 Provider 简单可替换，可能经 UnaAPI 网关调用，但 ERP Token、买家隐私和业务账务保持隔离；AI 不直接调用 Mercado Libre 写 API。

有实际自动操作需求后，再将 AI 请求映射到与人工一致的服务端校验和写入路径；不创建独立 AI 微服务或通用 Agent 框架。

## 5. 只做需要的同步

最开始：服务器保存店铺与已同步业务数据，客户端在线分页查询；缓存和草稿按需实现。多设备登录后看到同一份**已保存**数据即可。
完整增量日志/SSE/离线 outbox/冲突合并不是 M0 必须项。未来若实现游标，不能用数据库 sequence 分配顺序冒充提交顺序。

## 6. 必要安全

服务端保存平台 Token，并启用 HTTPS 与 OAuth state；公网服务有有效登录会话；写接口核对店铺归属、目标、参数并进行最小审计。拒绝“为了简化”泄露平台密钥或允许无鉴权的敏感写入。
