# 领域模型、平台适配与任务执行契约（v1）

本文件规定最容易导致大面积返工的数据与动作边界。它不代替官方 API 规格；所有 endpoint/method/scope 以开发者文档和实测结果为准。

## 1. 核心领域与标识

- `Tenant`：独立公司/卖家组织；`User`、`Membership`：ERP 使用者和租户内角色/店铺范围。
- `StoreConnection`：一次授权连接及其健康状态；关联 Meli 账号、站点、权限、Token Vault 的逻辑引用。
- `MarketplaceSeller`：平台实际 seller 身份，跨境账户与本地站点卖家身份可不同。
- `CatalogProduct` / `UpProduct` / `ProductFamily` / `Variation`：商品主数据层，不能与站点刊登混成一个表。
- `SiteListing`：站点商品记录及 listing ID、状态、币种、销售条件、价格；同一全局 UP 可映射多个站点刊登。
- `InventoryPosition`：按站点、物流方式、仓/位置及版本维护库存，不将共享库存简单复制到各店。
- `Order`、`Pack`、`Shipment`、`Claim`、`BuyerMessage`：订单与售后独立聚合。
- `Command`、`Approval`、`Job`、`ExternalAttempt`、`AuditEvent`：写操作、执行和回读的证据链。

业务键必须带足平台/租户/卖家/站点作用域；平台对象 ID 不等于 ERP 内部主键。价格使用精确十进制和货币单位，时间使用 UTC 存储、前端按对应站点时区呈现。

## 2. Mercado Libre 适配层

业务层不直接拼 URL、HTTP method、access token、平台错误码；适配层输出规范化领域结果。至少区分：OAuth/Identity、CBT UP、传统 Item、订单物流、消息、索赔、促销及分类属性。

每一项官方 API 能力都需有契约记录：

| 字段 | 要求 |
| --- | --- |
| API / 适用站点 | 官方文档链接、验证日期、跨境/本土限制 |
| HTTP 契约 | method、路径模板、scope、限流/分页/错误 |
| 映射 | 原始平台 DTO → 自有领域对象 |
| 真实性 | 文档支持 / 假数据单测 / 沙盒不可用 / 真实受控验证 |
| 写入语义 | 幂等是否由平台保证、是否可逆、未知结果恢复策略 |

必须先用真实受控账号验证目标 CBT UP 权限和全球商品/当地销售条件映射，不从第三方反编译端点直接推断官方 API 可用性。

## 3. 写命令生命周期

    Created → Validated → AwaitingApproval? → Queued → Running
                                              ├─ Verified
                                              ├─ Rejected / Failed
                                              └─ UnknownOutcome → Reconciled / ManualReview

每条命令包含内部 command_id、tenant_id、store_connection_id、actor、目标实体及版本、请求摘要、风险分类、幂等键、审计 trace。高风险写入（退款、争议、批量改价、广告预算、批量退出促销）必须审批。

- `dry_run` 展示目标、字段 diff、风险与可能不可逆影响。
- 入队与命令创建必须在同一事务内持久化；任务状态与每次外部请求尝试必须可回查。
- 平台超时不能简单当“失败并重试”：对可能已经生效的写动作先按可查询的资源和业务键回读，确认是否已执行。
- 幂等键只保证本系统可检测的重复；若官方接口不保证幂等，就必须做回读/对账或人工处理，不能宣称 exactly-once。
- 批量任务暂停只阻止未启动的子任务；已发送的外部请求不保证可以取消。
- “回滚”仅用于已验证可逆的动作；不可逆动作应明确标注并提供补偿/人工处理流程。

## 4. 持久化任务与同步

首版优先使用 PostgreSQL 持久任务，Worker 可以独立进程执行但与 API 共 Go 代码库。任务框架需验证许可证、失败重试、可观测性、定时执行和中断处理；Redis 不是必须基础设施。

- 按 tenant、seller、site、endpoint 配额限流；429 使用 Retry-After（若返回）和带抖动退避。
- 死信/人工处理可见、可重放；订单/商品/消息分别维护数据水位。
- 平台通知入口快速确认，随后异步处理；必须去重、支持乱序、漏通知补拉与定期对账。
- 第一阶段无需完整双向离线同步引擎；优先服务器分页、带版本的缓存刷新、草稿和出站队列。
- 将来如引入变更日志游标，必须确保**游标可见顺序与提交顺序一致**：数据库 sequence 分配顺序不能直接等同事务提交顺序。
- 跨设备初期恢复服务端已保存的数据；离线设备本地文件与未同步草稿不自动跨设备转移。

## 5. AI 与业务动作分离

- `ReadTool`：只读查询；`SuggestTool`：标题、翻译、属性、客服草稿；`ActionTool`：受控写命令，不拥有平台 Token。
- 统一通过领域服务鉴权、最小数据脱敏、参数校验、规则引擎和审计，不允许模型直接执行任意 SQL 或 HTTP。
- AI 文案正式写入前验证：商品类目属性、语种、禁限词、字符长度与真实事实；墨西哥西语与巴西葡语必须按实际输出分别校验，不只校验英文。
- 提示词与模型版本可追踪；结构化响应有 schema 与失败回退；模型/供应商可替换（可通过 UnaAPI 适配），**不复用 UnaAPI 的身份、账务或业务数据库**。
- 高风险变更保留 human-in-the-loop，禁止自动发送索赔/退款等不可逆动作。

## 6. 安全与验收

- 租户隔离覆盖表查询、缓存、文件、任务和 AI 检索；测试应覆盖不同 tenant 与 store 的越权访问。
- 访问/刷新 Token 只在服务器密钥管理边界，使用并发刷新锁、新 refresh token 原子更新、撤销/重新授权流程。
- 记录平台响应追踪标识，不记录密钥和买家个人信息原文。
- 集成测试覆盖并发刷新、429、超时后回读、重复任务、Worker 崩溃、站点映射和货币精度。
