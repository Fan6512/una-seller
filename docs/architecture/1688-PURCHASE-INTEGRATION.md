# 1688 采购关联路线图（UNA-SELLER / 2026-11-21）

状态：**M3-1688-A 实施中；M3-1688-B 官方接入条件待核实**。仅服务 Mercado Libre CBT 跨境卖家；避免引入 Redis、队列或第二套登录系统。

## 1. 业务事实和边界

卖家在 Mercado Libre 收到销售订单，在 1688 向厂家采购，由厂家通过国内快递发至货代仓，货代仓收件后转交 Mercado Libre 官方/指定物流，最终买家签收。以下事实不得混淆：

- **Mercado Libre 销售订单**：销售币种、状态和 Shipment ID 来自平台，不等于货物已发出。
- **1688 买家采购订单**：人民币采购总金额、付款/厂家发货状态、国内快递包裹，仅从人工输入或获授权的 1688 买家账号读取。
- **货代仓签收、官方物流交接、买家签收**：独立的真实物流事件；没有可信事件来源时保持“待接入”，不得猜测。
- 不自动下单、付款、确认收货、提交 Mercado Libre 发货或改写平台订单状态。采购人民币成本不可直接和 Mercado Libre 美元/当地币销售金额相减作为利润。

## 2. 本轮 M3-1688-A：采购关联工作台（零新表）

使用既有 `app.meli_order_purchases`、`GET/POST .../orders/{id}/purchase`：

1. 在订单列表直接显示“待关联/已关联”、1688 采购订单号和**人工录入**人民币采购成本；未填写则显示“待补录”。
2. 提供“全部/待关联/已关联”**服务端筛选**，在分页之前筛选（避免仅过滤当前页造成遗漏），支持在当前页通过完整 1688 采购单号搜索。
3. 点击“关联采购”进入现有右侧订单详情，保存后自动刷新列表。复用既有版本戳冲突保护和 8 秒 GET / 25 秒 POST 约束。
4. 关联查询始终按 `store_id + site_id + logistic_type + seller_id + order_id` 五维联合键，不把另一个 CBT 子卖家同号订单的采购信息带进来。
5. 只扩展现有订单 GET 返回中的脱敏采购字段，**不访问 1688 外部 API**，不增加新迁移，不改生产部署。
6. 维持现阶段“一张 Mercado Libre 订单关联一张 1688 采购单”数据模型；若实际出现拆单/合单，再依据真实业务升级，不提前复杂化。

本轮验收：CI + PostgreSQL 集成测试覆盖已关联/待关联筛选、关联金额、不同子卖家映射隔离、无效筛选拒绝；Windows 手动验收通过后再合并。

## 3. 下一轮 M3-1688-B：1688 买家账号官方授权（前置条件）

官方入口：<https://aop.alibaba.com/>。应先由项目负责人核实：

- 自有 1688 开放平台应用能否获批买家账号授权，账号类型、权限范围、OAuth 回调域名是否支持。
- 获得**买家视角订单列表与详情**，及**买家视角国内物流运单/轨迹**的实际 API method、签名规范、AppKey/Secret、授权及刷新机制、调用额度。以应用控制台可用权限和官方文档为准；不盲用第三方聚合 API 名称。
- 实际 1688 买家账号是否能授权该应用；用一笔本人实际采购的订单只读验证金额、付款和快递信息（注意脱敏）。
- AppSecret、OAuth Token、refresh 凭据必须在 Go 服务端保管和加密，桌面端只显示授权状态和查询结果；不保存 Cookie，不要求用户提供账号密码给桌面端。
- 单独“1688 买家账号”身份与 Mercado Libre CBT OAuth/子卖家映射解耦；不复用后者 Token。

通过上面全部条件后再开**独立 Draft PR**做最小闭环：授权/刷新 -> 单笔1688买家采购订单只读查询 -> 手动确认关联 -> 采购总金额来源标记 -> 国内物流只读展示。先只读、后增量；绝不自动覆盖用户人工录入成本。不同步物流事件前不能显示“厂家已发货”。
